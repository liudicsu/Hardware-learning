## Why every robot project from now on lives in a repository

From this lesson on, every project gets a Git repository. A repo is a project folder plus its complete history: every saved version, who changed it, when, and why. That history is the point. When the robot stops working after "one small change", compare it with the last version that worked, see the exact lines that differ, and go back if needed. Without it you end up with `robot_final_v3_really`.

Git is the version-control tool; GitHub is a website that hosts Git repositories. Git works offline. GitHub makes the project visible: a public profile of repos is a portfolio, and recruiters often read the README before a line of code. Robots mix scripts, sketches, wiring notes, calibration numbers and photos, and a repo keeps them together and dated. This lesson's first repo holds the month-1 scripts `ohm.py` and `log.py`.

## The mental model: snapshots, three areas, and a moving label

A **commit** is a snapshot of the whole project at one moment, plus a message, an author, a timestamp and a pointer to its parent. Git stores snapshots and computes differences when you ask, so you can always return to a complete working state.

Three areas matter: the **working directory** (files on disk, including unstaged edits), the **staging area** or index (a draft of the next commit, filled by `git add`), and the **repository** (the `.git` folder, where commits live). `git commit` turns whatever is staged into a new commit; unstaged edits stay out. That is the most useful idea in Git: **you choose what goes into each snapshot.**

A **branch** is a movable label pointing at one commit. `main` is the default. Committing on a branch moves its label forward. A branch is not a folder copy; it is a name, which is why creating one is instant. **HEAD** means where you are: normally it points to a branch, which points to a commit. If HEAD points directly at a commit, you are in detached HEAD state.

```text
working directory ──git add──▶ staging area ──git commit──▶ repository
   (your edits)                    (index)                   (.git)

main     A ───── B ───── C
                          ╲
feature                    D ───── E
                                   ▲
                                  HEAD
```

A, B and C are on `main`. `feature` started at C and has two more commits, D and E. HEAD points to `feature`, so the files on disk look like snapshot E. Switch to `main` and the files become snapshot C; D and E still exist because the `feature` label still points at them.

## One-time setup

Install Git from git-scm.com or your package manager, then check `git --version`. You want 2.30 or newer; this lesson uses `git switch` and `git restore`, which arrived in 2.23. On Windows, Git for Windows includes Git Bash. On macOS, `xcode-select --install` is usually enough.

Set your identity once per machine:

```bash
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main
```

`--global` means every repository on this computer; drop it inside a repo to use a different identity there. Use the email attached to GitHub, or GitHub's noreply address. The third line makes new repos start on `main` instead of the older `master`.

Create a GitHub account, then authenticate. The easiest way is the GitHub CLI:

```bash
gh auth login
```

Choose GitHub.com, pick SSH or HTTPS, and finish in the browser.

Or use an SSH key:

```bash
ssh-keygen -t ed25519 -C "you@example.com"
```

Press Enter for the default path, then set a passphrase. `id_ed25519` is your private key and never leaves the machine; `id_ed25519.pub` is the public half. Copy it with `cat ~/.ssh/id_ed25519.pub`, then add it on GitHub under Settings → SSH and GPG keys → New SSH key. Test it:

```bash
ssh -T git@github.com
```

The first connection asks whether to trust the host; type `yes`. A reply like `Hi <username>! You've successfully authenticated, but GitHub does not provide shell access.` is a success; the last part is normal.

## The everyday loop: edit, stage, commit

Assume `ohm.py` and `log.py` are in your current folder. Start the repo:

```bash
mkdir month1-tools
cd month1-tools
git init
```

`git init` prints `Initialized empty Git repository in .../.git/`. The hidden `.git` folder is the entire history; do not edit or delete it. If you run `git init` in your home folder by mistake, delete that `.git` before it tracks your entire home directory.

Create `.gitignore` before the first commit:

```text
.venv/
__pycache__/
*.pyc
.DS_Store
```

`.venv/` is a virtual environment full of machine-specific binaries, `__pycache__/` and `*.pyc` are generated bytecode, and `.DS_Store` is macOS Finder metadata. A trailing `/` matches a directory; `*` matches any characters. Ignore rules only affect **untracked** files. If something is already committed, remove it from the index with `git rm -r --cached <path>`.

Copy the scripts in, then run `git status`:

```text
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
        .gitignore
        log.py
        ohm.py

nothing added to commit but untracked files present (use "git add" to track)
```

Untracked means Git sees the file but is not following it. Stage exactly what you want:

```bash
git add ohm.py log.py .gitignore
```

The same three files are now in the staging area. Commit them:

```bash
git commit -m "Add Ohm's law calculator and measurement log"
```

```text
[main (root-commit) 9f2c1ab] Add Ohm's law calculator and measurement log
 3 files changed, 84 insertions(+)
 create mode 100644 .gitignore
 create mode 100644 log.py
 create mode 100644 ohm.py
```

`9f2c1ab` is the short hash. `root-commit` means this is the first commit, with no parent. Check the history:

```bash
git log --oneline
```

```text
9f2c1ab (HEAD -> main) Add Ohm's law calculator and measurement log
```

Both HEAD and `main` point here. Later, `git log --oneline --graph --all` draws branches as lines.

### The two diffs

`git diff` compares the **working directory with the staging area**: what you changed but have not staged. `git diff --staged` compares the **staging area with the last commit**: exactly what the next commit will add. Change the `current` subcommand's output format in `ohm.py` from `{ma:.1f}` to `{ma:.2f}` (two decimal places) and run:

```bash
git diff
```

```text
diff --git a/ohm.py b/ohm.py
index bd6542e..ac31ca1 100644
--- a/ohm.py
+++ b/ohm.py
@@ -37,7 +37,7 @@ def main() -> None:
 
     if args.command == "current":
         ma = current(args.volts, args.ohms) * 1000
-        print(f"{ma:.1f} mA")
+        print(f"{ma:.2f} mA")
     elif args.command == "divider":
         v = divider(args.vin, args.r1, args.r2)
         print(f"{v:.3f} V")
```

`@@ -37,7 +37,7 @@` means the hunk starts at line 37 and shows 7 lines of both versions; lines without a `-` or `+` prefix are context, and `def main() -> None:` after the `@@` names the enclosing function. After the change, `python ohm.py current --volts 5 --ohms 220` prints `22.73 mA` instead of `22.7 mA`. The `-` line is old, the `+` line is new. Nothing is staged, so `git diff --staged` is empty. After `git add ohm.py`, `git diff` is empty and `git diff --staged` shows the same line. Read `git diff --staged` before every commit: a password, a huge data file or an unrelated experiment should be unstaged, not committed.

## Putting it on GitHub

Create the empty repository on github.com: name it `month1-tools`, choose Public for a portfolio project, and **do not** add a README, `.gitignore` or license if you already have local commits. Each option creates a commit on GitHub that your local history lacks, so the first push is rejected as a non-fast-forward.

With the GitHub CLI, one command does it:

```bash
gh repo create month1-tools --public --source=. --push
```

`--source=.` uses the current repo and `--push` uploads `main` immediately.

The manual route:

```bash
git remote add origin git@github.com:<you>/month1-tools.git
git push -u origin main
```

Replace `<you>` with your username. `origin` is the conventional nickname for the remote. `-u` sets the upstream branch, so later `git push` and `git pull` know to use `origin/main`. For HTTPS use `https://github.com/<you>/month1-tools.git`; a personal access token is safer than your account password.

Check with `git remote -v`. Fix a typo with `git remote set-url origin <correct-url>`. If push says `src refspec main does not match any`, you have no commits yet or your branch is still `master`; run `git branch -M main` and push again. If the remote has a README, integrate it with `git pull --rebase origin main` first.

Afterward: **pull before you start, push when a coherent piece is finished**. `git pull` fetches and integrates remote commits; `git push` uploads yours. Neither backs up work you have not committed.

## Branches and merging

A branch lets you try something without touching `main`:

```bash
git switch -c feature/json-log
```

`-c` means create. `git branch` marks the current branch with `*`; `git status` says `On branch feature/json-log`. Edit `log.py` so each measurement becomes one JSON line, test it, and commit:

```bash
git add log.py
git commit -m "Write measurements as JSON lines"
```

The commit goes onto `feature/json-log`; `main` does not move. `git switch main` and the change disappears from your files, but it is not lost: the feature label still points at it. Merge it in:

```bash
git merge feature/json-log
```

If `main` has not moved since the branch was created, Git does a **fast-forward**: it slides the `main` label forward, with no merge commit. If both branches have new commits, Git creates a **merge commit** with two parents. `git log --oneline --graph --all` shows either result. Delete the label:

```bash
git branch -d feature/json-log
```

`-d` refuses to delete an unmerged branch, which is a useful guard. `-D` forces it.

### Structure of a merge-conflict marker

A conflict happens when both branches change the same lines, or one deletes a file the other edits. Git stops the merge and marks the file:

```text
<<<<<<< HEAD
data = {"voltage": voltage, "current": current}
=======
data = {"v": voltage, "i": current}
>>>>>>> feature/json-log
```

The top block is the version on your current branch (`HEAD`, here `main`); the bottom is the incoming branch. **Edit the file by hand** until it contains the code you want, delete all three marker lines, then:

```bash
git add log.py
git commit
```

`git add` marks the file resolved; `git commit` records the merge, with a message Git pre-fills. If the merge becomes unmanageable, `git merge --abort` restores the pre-merge state. Small branches merged often produce few conflicts; a branch that lives for weeks touching every file produces many conflicts.

## Writing a README someone can follow

On GitHub the README renders under the file list. It is often the first thing a visitor sees, and sometimes the only thing a recruiter reads. A photo, a one-line description and a wiring table beat three paragraphs of background. It is also for future you, who will not remember the pinout.

```markdown
# Bench Logger — 5 V rail monitor

A breadboard logger that records voltage and current once per second and prints one JSON object per line over USB.

![Bench Logger with the INA219 and LCD connected](docs/photo.jpg)

## What it does

An Arduino Uno reads an INA219 voltage/current sensor once per second, shows the latest values on a 16×2 I2C LCD, and sends a JSON line to the serial port. The host script `host/log.py` saves those lines to `measurements.jsonl`, so the data survives a reboot.

## Parts

| Qty | Part | Notes |
| --- | --- | --- |
| 1 | Arduino Uno R3 | any Uno-compatible board works |
| 1 | INA219 breakout | I2C address 0x40 |
| 1 | 16×2 I2C LCD | I2C address 0x27 |
| 1 | Breadboard | half-size is enough |
| — | Jumper wires | keep the I2C wires short |
| 1 | 5 V load | a USB lamp was used for testing |

## Wiring

| From | To | Note |
| --- | --- | --- |
| Uno 5V | INA219 VCC | power |
| Uno GND | INA219 GND | common ground |
| Uno A4 | INA219 SDA | I2C data |
| Uno A5 | INA219 SCL | I2C clock |
| Uno 5V | LCD VCC | power |
| Uno GND | LCD GND | common ground |
| Uno A4 | LCD SDA | shares the bus with the INA219 |
| Uno A5 | LCD SCL | shares the bus with the INA219 |
| INA219 VIN+ | 5 V supply + | current flows in here |
| INA219 VIN− | load + | |
| load − | 5 V supply − | return path |

The INA219 sits in series with the load. The LCD and the sensor share one I2C bus.

## How to run

1. Install the Arduino libraries `Adafruit INA219` and `LiquidCrystal I2C`.
2. Flash `firmware/bench_logger/bench_logger.ino`.
3. On the host computer:

       python -m venv .venv
       source .venv/bin/activate
       pip install -r requirements.txt
       python host/log.py --port /dev/ttyACM0 --baud 115200

   On Windows the port looks like `COM5`, and the activate command is `.venv\Scripts\activate`.

## What broke and how I fixed it

The first version printed `nan` every few seconds. The INA219 and the LCD share one I2C bus, and I had used 30 cm jumper wires with no external pull-ups while running the bus at 400 kHz. I shortened the wires to 10 cm, added 4.7 kΩ pull-ups from SDA and SCL to 5 V, and dropped the clock to 100 kHz; the `nan` readings stopped. I still saw about one bad sample every few hours, so the logger now takes three readings and records the median. That is a workaround, not a perfect fix, and it is written down here so the next person knows the limit.

## Next steps

- Calibrate the INA219 against the bench multimeter at 100 mA and 1 A.
- Log to an SD card so a laptop is not required.
- Power it from a 2S LiPo pack with a 5 V buck converter.
- Print an enclosure so the boards cannot short on the bench.
```

The **What broke** paragraph is what makes this engineering rather than a tutorial. A tutorial says "connect A to B, it works". An engineer records the symptom (`nan`), the suspected cause (long wires, no pull-ups, 400 kHz), the changes made, and the remaining limitation. That documents your testing, your analysis of the failure, and the remaining limitations; it also answers "tell me about a bug you fixed" better than a prepared answer.

Shoot the photo from above with the wiring visible, compress it well under 1 MB, and commit it as `docs/photo.jpg`. A blurry photo of a closed box provides no useful information.

## Good commit messages

Write for the person who will read the log six months from now, usually you. Use the **imperative mood**: complete "If applied, this commit will ___". Git's own messages do this (`Merge branch ...`, `Revert ...`), and the log reads like a list of actions.

Be specific:

```text
Fix divider calculation when R2 is zero
Add JSON output to log.py
Clamp the ADC reading to 0–1023 before scaling
Move serial parsing into read_sample()
```

Not:

```text
update
stuff
final final v2
fixed bug
```

Keep the first line under 50 characters. To explain **why**, leave a blank line and write a body wrapped at about 72 characters; the diff already shows what changed.

Commit small and often, one logical change per commit: a bug fix, a feature, a rename. Commit when the script runs or the test passes, and before a risky refactor. Do not mix formatting with behaviour; the diff becomes unreadable and `git bisect` cannot identify the commit that introduced the problem. A hundred small commits beat one 3,000-line commit called `big update`.

## Undo reference

Mistakes are normal. The skill is choosing an undo that does not make things worse.

| Situation | Command |
| --- | --- |
| Discard unstaged changes in one file | `git restore <file>` |
| Unstage a file, keep the edits | `git restore --staged <file>` |
| Fix the last commit message, not pushed | `git commit --amend` |
| See an old version | `git switch --detach <hash>` or `git show <hash>:file` |
| Undo a pushed commit safely | `git revert <hash>` |

- `git restore` is destructive; copy the file first if unsure.
- `git commit --amend` rewrites the hash. Use it only before pushing; on a shared branch, prefer `git revert`. If you must rewrite your own pushed branch, use `git push --force-with-lease`, never force-push `main`.
- `git switch --detach <hash>` is read-only exploration; return with `git switch main`. `git show <hash>:ohm.py > /tmp/ohm-old.py` saves an old file.
- `git revert <hash>` is the public undo: a new commit reverses the change and teammates pull normally. For a merge commit, Git may ask for `-m 1`.
- `git reflog` shows where HEAD has been and can rescue a lost local commit; it is temporary.

<Callout type="warn" title="Never commit secrets">
Passwords, API keys, Wi-Fi credentials, tokens and private keys never belong in a commit. Once pushed, a secret is leaked: deleting the file later does not remove it from history, and clones may still have it. Rotate it first, then clean history with `git filter-repo` or BFG. Keep secrets in `.env` or `secrets.h`, list them in `.gitignore`, and check `git diff --staged` before committing.
</Callout>

<Callout type="tip" title="Do not commit large binaries">
Git stores every version, so a 100 MB video stays in the repo and every clone downloads it. Link to YouTube or Drive instead. Use Git LFS only for files that truly belong, and compress photos.
</Callout>

## Common mistakes and a before-you-move-on checklist

<Quiz id="q3" question="You pushed a commit that broke things; teammates already pulled. Safest undo?" options={["git reset --hard and force-push", "git revert <hash> and push", "Delete the repository"]} answer={1} explanation="git revert creates a new commit that reverses the bad one, so teammates who already pulled can pull again safely. git reset --hard rewrites shared history and a force-push breaks their clones." />

Mistakes to avoid:

- `git init` in the wrong folder. Check `git rev-parse --show-toplevel`; delete the stray `.git`.
- Adding `.gitignore` after committing `.venv`; ignore rules do not affect tracked files. Use `git rm -r --cached .venv`.
- `git add .` without reading `git diff --staged`: it will stage a secret or a 200 MB video.
- Working directly on `main` and force-pushing to clean up.
- Pulling with uncommitted changes. Commit first, or `git stash push -m "wip"` and `git stash pop`.
- Committing conflict markers, writing `update`, or shipping no README.
- Treating GitHub as a backup, or nesting a repo inside another repo.

Before moving on, can you answer "yes" to all of these?

- Git is installed and configured with my name, email and `main` as the default branch.
- I created `month1-tools`, added a `.gitignore`, staged the scripts and made a commit.
- I can explain the working directory, staging area and repository, and what each diff compares.
- I pushed the repo and know what `git push -u origin main` does.
- I created a branch, merged it into `main` and deleted it.
- I resolved a conflict by hand and know why `git add` comes before `git commit`.
- My README has a photo, parts list, wiring table, run commands and a factual "what broke" paragraph.
- I can choose the right undo, and I know why secrets are rotated and videos do not belong in Git.

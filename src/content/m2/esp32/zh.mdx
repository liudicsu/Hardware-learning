## 为什么换到 ESP32

两节 Uno 课已经给你搭好了机器人程序的基本骨架：读输入、做判断、驱动输出，再把发生的事通过串口讲给你听。你也学会了用 `millis()` 取代 `delay()`，以及让中断服务函数尽量短。换一块板子，这些思路一点都不会浪费；真正变化的是板子能同时做多少事，以及不用外接模块就能连上什么。

换板的理由通常很具体。你想让机器人连上 Wi-Fi，用手机就能看到它的状态；你想用蓝牙接一只手柄或一个配置 App；你需要更快的时钟来跑控制运算，需要更大的内存来放缓冲区和网页，或者需要第二个核心，让联网不再和电机控制抢时间。还有一点可能出乎意料：具备这些能力的 ESP32 开发板，常常比一块 Uno 兼容板还便宜。

ESP32 是一个系列，不同型号并非每个细节都能互换。你最先会遇到的三种是：

| 芯片 | CPU | 内存 | 无线 | 备注 |
| --- | --- | --- | --- | --- |
| 经典 ESP32 | 双核 Xtensa LX6，最高 240 MHz | 520 KB SRAM | Wi-Fi 2.4 GHz + 蓝牙经典 + BLE | 网上大多数旧教程针对的就是它 |
| ESP32-S3 | 双核 Xtensa LX7，最高 240 MHz | 512 KB SRAM | Wi-Fi 2.4 GHz + BLE 5（没有蓝牙经典） | 原生 USB；本课程推荐的主力板 |
| ESP32-C3 | 单核 RISC-V，最高 160 MHz | 400 KB SRAM | Wi-Fi + BLE 5 | 体积小、价格低，例如 Seeed XIAO ESP32-C3 |

型号名字背后有一个关键区别：S3 更新、更强，但砍掉了蓝牙经典（Bluetooth Classic）；C3 小巧便宜，单核 RISC-V 跑传感器和 Wi-Fi 足够，但留给复杂控制运算的余量不多；经典 ESP32 则处在中间，也是现存教程覆盖最广的一颗。

所以本课程的购买建议很直接：主力买一块 ESP32-S3 开发板，再备一块经典 ESP32。S3 给你原生 USB、较新的外设和继续折腾的空间；经典板花不了多少钱，却能让你在照抄 S3 出现之前的旧教程时，代码一行不改就跑起来。

<Resource id="esp32-s3-devkit" />

和 Uno 相比，速度差距很容易被低估。拿 ESP32-S3 和 Arduino Uno（ATmega328P）对照：

```text
时钟:  240 MHz / 16 MHz = 15×
内存:  512 KB / 2 KB   = 256×
位宽:  32 位 vs 8 位
```

（经典 ESP32 还略多一点，有 520 KB。）时钟快 15 倍，不等于实际代码快 15 倍——访存、Wi-Fi 协议栈和库的开销都要分走一部分。但它意味着你可以放心使用浮点运算、JSON 字符串和网页服务，而不至于逼近性能上限。内存的差距更要紧：256 倍的工作内存，决定了你是“能把整个网页放进一个字符串”，还是“只能分块往外吐”。32 位处理器还能一次处理一个指针或地址，8 位核心则要拆成好几次。

代价在逻辑电平上。Uno 是 5 V 板，ESP32 是 <Term id="3v3-logic">3.3 V</Term> 板，而且它的引脚不耐 5 V。下文“3.3 V 逻辑”一节会讲这在实验台上具体意味着什么。现在先记住一句话：能力更强，也意味着更不容错。

## 环境搭建与第一次上传

为 Uno 装好的 Arduino IDE 可以继续用，但它原本不认识 ESP32，必须先告诉它去哪里找板子定义。Windows、macOS 和 Linux 的步骤一样，只是不同版本的菜单名称略有出入。

1. 打开 **Preferences**（或 **Settings**），找到“附加开发板管理器网址”一栏。
2. 粘贴下面这个地址：

```text
https://espressif.github.io/arduino-esp32/package_esp32_index.json
```

3. 打开 **Tools → Board → Boards Manager**，搜索 `esp32`，安装 **esp32 by Espressif Systems**。下载量不小，耐心等它装完。
4. 经典板选 **ESP32 Dev Module**，S3 选 **ESP32S3 Dev Module**。如果你用的是 XIAO 这类有名字的板子，就选与它完全对应的条目。
5. 选中插上板子后出现的那个串口。

S3 有一个容易被忽略的细节。很多 S3 板有两个 USB 口：一个直接连芯片的原生 USB，另一个连独立的 USB 转串口芯片。如果你用原生 USB 口，要到 **Tools** 里把 **USB CDC On Boot** 设为 **Enabled**。不设的话，程序照常运行，但 `Serial` 的输出哪儿也不去，你会误以为上传失败，其实并没有。只有一个 USB 口的板子也要检查这个选项，有些出厂就是关的。

上传失败，多数是连接问题而不是代码问题。最可靠的恢复办法是手动进下载模式：按住 **BOOT**，点一下 **RESET**（有的板标 **EN**），松开 **BOOT**，再点上传。也可以换板上的另一个 USB 口、换一根线。只能充电的 USB 线没有数据线芯，插上板子会亮、上传却永远失败，症状和板子坏了几乎一样。

下面是第一个程序：它让 GPIO 2 上的外部 LED 闪烁，在 ESP32-S3 上还会让板载 RGB LED 一起闪烁，并报告自己是什么芯片：

<CodeSource path="examples/month-2/esp32/chip_info/chip_info.ino" />

```cpp
// Blink an LED and report which chip this is.
// LED_PIN drives an external LED through a 220 Ω resistor on GPIO 2. That works on every
// board; on many classic ESP32 DevKits GPIO 2 is also the on-board LED.
// The ESP32-S3-DevKitC-1 has no plain on-board LED: it has one addressable RGB LED, on
// GPIO 38 on board v1.1 and on GPIO 48 on the initial v1.0 (Espressif user guide).
const int LED_PIN = 2;
#if CONFIG_IDF_TARGET_ESP32S3
const int RGB_PIN = 38;  // DevKitC-1 v1.1; set 48 for the initial v1.0 board
#endif

void setup() {
  Serial.begin(115200);
  delay(1000);  // give the USB serial port a moment to appear
  pinMode(LED_PIN, OUTPUT);
  Serial.printf("Chip: %s rev %d, %d core(s), %lu MHz\n",
                ESP.getChipModel(), ESP.getChipRevision(),
                ESP.getChipCores(), (unsigned long)ESP.getCpuFreqMHz());
  Serial.printf("Flash: %lu bytes\n", (unsigned long)ESP.getFlashChipSize());
}

void loop() {
  digitalWrite(LED_PIN, HIGH);
#if CONFIG_IDF_TARGET_ESP32S3
  rgbLedWrite(RGB_PIN, 0, 32, 0);  // dim green
#endif
  delay(200);
  digitalWrite(LED_PIN, LOW);
#if CONFIG_IDF_TARGET_ESP32S3
  rgbLedWrite(RGB_PIN, 0, 0, 0);   // off
#endif
  delay(800);
}
```

这段代码里有两样东西是 Uno 上没有的。第一是 `Serial.printf()`，它来自 C 语言的格式化输出：`%s` 代表字符串，`%d` 代表整数，`%lu` 代表无符号长整数。它省掉了五六次 `Serial.print()` 和一串分隔符。第二是 `ESP` 对象：`ESP.getChipModel()` 返回芯片型号，`getChipRevision()` 返回版本，`getChipCores()` 返回核心数，`getCpuFreqMHz()` 返回主频，`getFlashChipSize()` 返回 Flash 容量（字节）。

上传完成后，把串口监视器开到 **115200 baud**。你应该能用文字看出两行信息：一行以 `Chip:` 开头，后面是型号、版本、核心数和主频；另一行以 `Flash:` 开头，后面是 Flash 的字节数。具体数值取决于你手上的板子，所以要照着读，而不是背一个固定答案。外部 LED（在 S3 上还有暗绿色的板载 RGB LED）应该亮 200 ms、灭 800 ms。这两个程序都为经典 ESP32 和 S3 编译过，但没有在真实硬件上运行，因此这里不展示任何串口输出；真实数字由你的板子给出。

最容易让人失望的是那颗 LED。很多经典 DevKit 的板载 LED 是一颗接在 GPIO 2 的普通 LED，但 ESP32-S3-DevKitC-1 没有普通板载 LED，只有一颗可寻址 RGB LED。`digitalWrite` 驱动不了它：它需要一段严格定时的串行数据流，`rgbLedWrite(pin, r, g, b)` 负责发送。这块板同时有初版 v1.0 和 v1.1 在售，两者的 RGB LED 引脚不同：v1.1 用 GPIO 38，初版 v1.0 用 GPIO 48（[v1.1 用户指南](https://docs.espressif.com/projects/esp-dev-kits/en/latest/esp32s3/esp32-s3-devkitc-1/user_guide_v1.1.html#hardware-revision-details) 与 [v1.0 用户指南](https://docs.espressif.com/projects/esp-dev-kits/en/latest/esp32s3/esp32-s3-devkitc-1/user_guide_v1.0.html)）。因此程序明确写 `RGB_PIN = 38`，而不是用 `RGB_BUILTIN`：在 arduino-esp32 3.3.12 中，该宏由 `PIN_RGB_LED` 定义为 48，也就是 v1.0 的引脚，在 v1.1 板上点不亮（[pins_arduino.h](https://github.com/espressif/arduino-esp32/blob/3.3.12/variants/esp32s3/pins_arduino.h)）。如果你的 RGB LED 一直不亮，把 `RGB_PIN` 改成 48。`#if CONFIG_IDF_TARGET_ESP32S3` 让这段 RGB 代码不进入经典 ESP32 的编译。就算完全不亮，串口里那份芯片报告仍然证明上传成功、芯片在运行——LED 只是接线细节，不代表上传失败。

## 3.3 V 逻辑与引脚陷阱

ESP32 用 3.3 V 供电。它的 GPIO **不耐 5 V**：数据手册给出的绝对最大值大约在 3.6 V，把 5 V 信号硬灌进引脚，可能当场损坏输入级，也可能“暂时还能用”，让你误以为没事。常见的 5 V 来源包括 HC-SR04 的 echo 引脚、5 V Arduino 的输出，以及一些上拉到 5 V 的老传感器模块。

标准解法有两种。**电平转换器（level shifter）** 是一块专做这件事的小模块，双向总线（例如 I2C）就该用它。**分压器（voltage divider）** 则是便宜的单向方案：两只电阻把 5 V 信号先降到安全范围，再送进引脚。取上电阻 1 kΩ、下电阻 2 kΩ：

```text
R上 = 1 kΩ，R下 = 2 kΩ，Vin = 5 V
R总 = 1 kΩ + 2 kΩ = 3 kΩ
I = Vin / R总 = 5 V / 3 kΩ = 1.667 mA
Vout = I × R下 = 1.667 mA × 2 kΩ = 3.333 V
验算: 5 V × 2 / (1 + 2) = 10 / 3 = 3.333 V
```

分压器里只流过约 1.7 mA，完全无害；输出为 3.333 V，刚好低于 3.6 V 的上限，并比 ESP32-S3 的高电平输入阈值高 0.86 V：[ESP32-S3 数据手册](https://www.espressif.com/sites/default/files/documentation/esp32-s3_datasheet_en.pdf) v2.2（表 5-4）给出 <Term id="logic-thresholds">VIH</Term> = 0.75 × 3.3 V = 2.475 V，VIL = 0.25 × 3.3 V = 0.825 V。0.86 V 的余量是个标称值：它假设信号是理想的 5.000 V，且 VDD = 3.3 V。当 VDD = 3.6 V 时，VIH = 0.75 × 3.6 V = 2.7 V，余量为 0.63 V。如果 Uno 的输出处于数据手册的下限，即 20 mA 时 VOH = 4.2 V，分压后得到 2.8 V，余量为 0.325 V；而在分压器 1.7 mA 的负载下，实际输出接近 5 V。如果两种最坏情况同时发生，余量会缩小到 2.8 V − 2.7 V = 0.1 V。这个数字假设电阻是精确值。用 ±1 % 的电阻，最坏情况（1 kΩ 偏大、2 kΩ 偏小）得到 2.78 V，余量约 0.08 V；用 ±5 % 的电阻得到 2.705 V，余量只有约 0.005 V，实际上等于零。这就是第一个月学过的分压算术，只是这次它的用途是保护引脚。

<Falstad title="把 5 V 信号分压到 3.3 V 输入" circuit="levelDivider" height={440} />

用法如下：

1. 左边的方波源就是一路缓慢切换的 5 V 逻辑信号。信号为高时，中点的探针读 3.333 V；为低时读 0 V。
2. 双击 2 kΩ 电阻，把它改成 3.3 kΩ。先写下你的预测，再按运行。
3. 新电平是 5 V × 3.3 / (1 + 3.3) = 16.5 / 4.3 = 3.837 V，约 3.84 V，对 3.3 V 引脚来说太高了。关键在比例而不是电阻的绝对值：1 kΩ 配 2 kΩ 的输出是输入的 2/3（相当于除以 1.5），1 kΩ 配 3.3 kΩ 的输出是输入的 3.3/4.3 ≈ 0.77（只相当于除以约 1.3）。

分压器适合单向、不太快的信号，例如按键、低频传感器输出或慢速串口。它不适合 I2C 或高速总线：电阻和导线电容构成低通滤波器，边沿被拖慢，总线就会时好时坏。那种场合请用真正的双向电平转换器。

电流是 3.3 V 故事的另一半。GPIO 的电流要留足余量，目标放在 20 mA 以下，并查数据手册确认所有引脚加起来的总限额。电机、舵机、继电器和 LED 灯带永远不要直接接引脚，而是像第一个月那节晶体管课讲的那样，用三极管或 MOSFET 从独立电源驱动。

### 经典 ESP32 上要避开的引脚

大多数 GPIO 都可以自由使用，但少数几个引脚被系统占用，或者行为出人意料。动手接线之前先记住这份清单，因为它们的故障看起来都像软件 bug。

- **GPIO 6–11** 接在 Flash 芯片上，永远不要用。很多模块甚至没有把它们引到排针。
- **GPIO 34–39** 只能输入，没有输出驱动，也没有内部上拉，写 `INPUT_PULLUP` 在它们身上不起作用。不过它们属于 ADC1，在 Wi-Fi 项目里做模拟输入反而很宝贵。
- **<Term id="strapping-pin">启动绑定引脚（strapping pin）</Term> GPIO 0、2、5、12、15** 会在启动瞬间被读取，用来决定启动模式和 Flash 电压。这些脚上的上拉、下拉或外接器件都可能让板子起不来。经典陷阱是 **GPIO 12 在启动时为高**：芯片会选错 Flash 电压，程序根本不会开始跑。如果板子单独上电正常、一接传感器就不启动，先怀疑 strapping 引脚。
- **Wi-Fi 开启时，ADC2 的引脚读不了**：Wi-Fi 驱动占用了那个转换器。Wi-Fi 项目里的模拟输入请用 ADC1，也就是 GPIO 32–39。

### ESP32-S3 上要留意的引脚

S3 是本课程的主力板，因此它单独有一份名单，内容取自 ESP32-S3 数据手册 v2.2（第 2.3.4 节，Restrictions for GPIOs and RTC_GPIOs）以及 [ESP32-S3-WROOM-1 模块数据手册](https://www.espressif.com/sites/default/files/documentation/esp32-s3-wroom-1_wroom-1u_datasheet_en.pdf)：

- **启动绑定引脚（strapping pin）GPIO 0、3、45、46** 在复位时被采样，用来选择启动模式和其他启动选项；GPIO 0 是 DevKitC-1 上的 BOOT 按键。不要在这些引脚上外接上拉、下拉或负载。
- **GPIO 19 和 20** 是原生 USB Serial/JTAG 接口的 USB D− 和 D+。把它们当 GPIO 使用会断开原生 USB 口。
- **GPIO 43 和 44** 是 UART0 的 TX 和 RX，DevKitC-1 的 USB 转 UART 桥用它进行上传和串口监视。
- **GPIO 26–32** 连接模块上的 Flash 和 PSRAM，不是可自由使用的 GPIO（在 WROOM-1 上，Flash 是模块板上一颗独立的芯片）。在采用八线（octal）PSRAM 的模块上，例如 WROOM-1 N8R8 和 N16R8，GPIO 35–37 也连接到 PSRAM，不能另作他用。
- **GPIO 39–42** 承载外部 JTAG 接口；不使用外部 JTAG 调试器时，它们就是普通 GPIO。
- **ADC1 是 GPIO 1–10**，ADC2 是 GPIO 11–20。与经典芯片一样，ADC2 与 Wi-Fi 驱动共用，因此在 Wi-Fi 项目中请用 ADC1 读取模拟输入。

在分配引脚之前，先查清模块上印着的 Flash 和 PSRAM 配置。

## ESP32 的 ADC

ESP32 的模数转换器（ADC）是 12 位的，也就是能给出 4096 个不同的编码值，编号 0 到 4095：0 代表量程底部，4095 代表顶部。位数比 Uno 的 10 位多，听起来是纯升级，但 ESP32 的 ADC 有几个 Uno 没有的脾气。

转换器前面的衰减器决定输入范围，Arduino 核心默认选择最大的设置 `ADC_11db`。[Arduino-ESP32 ADC 文档](https://docs.espressif.com/projects/arduino-esp32/en/latest/api/adc.html)给出该设置下的可测范围为 ESP32-S3 上的 0–3100 mV（经典 ESP32 上为 150–3100 mV），而 ESP32-S3 数据手册 v2.2（表 5-6）只对最高 2900 mV 的校准读数给出特性，总误差为 ±50 mV。因此可用范围约为 0–3.1 V，而不是完整的 3.3 V：3.2 V 和 3.3 V 的引脚都读 4095，这只能说明输入已达到或超过量程上限。在信号进入引脚之前，把可能达到 3.3 V 的信号分压到 2.9 V 以下。转换器在量程两端还有明显的非线性：中间一段还算老实，靠近 0 V 和靠近顶部时，同样的电压变化给出的编码变化和中间不一样。别指望它是一条理想直线。

实用的答案是 `analogReadMilliVolts(pin)`。它直接返回毫伏，并应用芯片出厂时写入的校准数据，能修掉大部分非线性和增益误差。不要自己拿 `analogRead()` 去缩放，需要电压就用这个校准过的函数。想要原始编码值时 `analogRead()` 仍然有用，但那是另一种需求。

为什么“自己换算”不够？取一个位于 12 位量程中点的原始值 2048，并假设参考电压是 3.3 V：

```text
2048 × 3.3 V / 4095 = 6758.4 / 4095 = 1.6504 V ≈ 1.65 V
```

同一个输入，校准后的读数可能相差约 0.1 V。默认的 12 dB 衰减在 ESP-IDF 中叫 ADC_ATTEN_DB_12（旧名 ADC_ATTEN_DB_11；旧名在 v4.4.7–v4.4.8、v5.0.5+、v5.1.3+ 及 v5.2–v5.5 中为已弃用别名（更早的 v4.4/v5.0/v5.1 版本中 DB_11 是正式名称），v6.0 起移除），在 Arduino 核心中叫 `ADC_11db`；如上所述，它的量程上限约为 3.1 V 而不是 3.3 V，高于 2.9 V 的读数不可靠。所以原始值 2048 更接近 2048 × 3.1 V / 4096 ≈ 1.55 V；每颗芯片的内部参考电压（标称 1.1 V，不同芯片在 1.0 到 1.2 V 之间）还会让结果再偏一些。这点差别正是出厂校准要消掉的东西。相信 `analogReadMilliVolts()`，并且多读几次取平均来压噪声：采样 8 次或 16 次，求和再除，是个好习惯。Wi-Fi 开着时坚持用 ADC1，同时记住 ADC 是拿自己的参考电压在量，而不是拿一个完美的 3.3 V 在量。

## Arduino、ESP-IDF 还是 MicroPython？

离开 Uno 之后，你会遇到三种给同一颗芯片编程的方式。它们并非在所有任务上一样好，选择取决于要做的事，而不是哪种“更专业”。

| 框架 | 什么时候选它 | 要注意什么 |
| --- | --- | --- |
| Arduino 核心 | 想最快做出能跑的机器人，想要最大的库生态，本课程就用它 | 隐藏了一部分 FreeRTOS 细节，一些底层功能开放得较晚 |
| ESP-IDF | 需要真正控制 FreeRTOS 任务、哪个核心跑什么、功耗模式和精确时序 | 上手更陡，样板代码更多，第一个闪灯之前要学更多概念 |
| MicroPython | 想快速试传感器，喜欢在 REPL 里一行一行试 | 垃圾回收（GC）的停顿会毁掉硬时序，不适合自平衡环 |

关键认识是：这三者是一条连续谱，而不是一次分叉（fork）。ESP32 的 Arduino 核心本身就架在 ESP-IDF 和 FreeRTOS 之上。你写 `setup()` 和 `loop()` 时，核心已经替你建好一个 FreeRTOS 任务，并从那里调用它们。<Term id="freertos-task">FreeRTOS 任务</Term>就是一个拥有自己的栈和优先级、由 FreeRTOS 调度器启动、暂停和恢复的函数，因此多个任务可以共享 CPU 核心，而不会互相阻塞。经典 ESP32 上，这个任务通常跑在一个核心，Wi-Fi 协议栈大部分跑在另一个核心，所以联网不会自动把控制代码卡死。你也可以在 Arduino 程序里调用 ESP-IDF 的函数，用 `xTaskCreatePinnedToCore()` 建自己的任务，把两种风格混在同一个项目里。

正是这种分层让课程从 Arduino 起步：现在走快路，需要时下层仍然够得着。如果以后 Arduino API 不能满足你对定时器控制或任务优先级的要求，转向 ESP-IDF 是往栈的下一层走，而不是推倒重来。

<Resource id="arduino-esp32" />

MicroPython 值得单独提醒。它非常适合读一个传感器、画一条曲线、五分钟验证一个想法；但它不适合必须固定频率运行的控制环，因为垃圾回收可能在必须严格执行时序的时刻暂停执行。200 Hz 的自平衡机器人承受不起几毫秒的停顿。用 MicroPython 探索，等时序变得要紧时，把最终的控制环换成 C++。

## 舵机信号与 LEDC 外设

普通舵机（hobby servo）并不接受一个“角度数字”。它期待每 20 ms 收到一个脉冲，也就是 50 Hz 的帧，而脉冲宽度决定角度。常见约定是 1.0 ms 对应 0°，1.5 ms 对应 90°，2.0 ms 对应 180°。很多舵机实际接受更宽的范围，大约 0.5–2.5 ms，但稳妥的做法是守着你那颗舵机数据手册给的范围。把舵机往机械限位之外驱，电机会顶着限位堵转、电流上升、发热，最后扫齿。

ESP32 用 <Term id="ledc">**LEDC**</Term> 外设产生这个信号。它是一块带硬件定时器和通道的 PWM 模块。Arduino-ESP32 核心 3.x 的 API 很简洁：先调一次 `ledcAttach(pin, frequency, resolutionBits)`，之后每次要改脉宽就调 `ledcWrite(pin, duty)`。分辨率以位为单位：n 位时 duty 一般取 0 到 2^n，所以 14 位对应 0 到 16384（2^14）。

<Formula label="脉冲对应的 LEDC duty">duty = pulse / period × 2^bits</Formula>

50 Hz 时周期是 1 / 50 = 0.02 s = 20 ms。一般来说，duty 取 2^bits 时整个周期都输出高电平（ESP-IDF LEDC 驱动）。ESP32-S3 在最高分辨率下是例外：它的 LEDC 定时器最多 14 位，ESP-IDF 的 LEDC 文档警告，定时器使用最大分辨率时 duty 不能设为 2^bits，否则硬件里的 duty 计数器会溢出。Arduino-ESP32 的 `ledcWrite()` 会把 2^bits − 1 及以上的值改写成 2^bits，所以在 S3 上用 14 位时，`ledcWrite(pin, 16383)` 也会碰到同样的问题。因此 S3 在 14 位下得不到 100 % 输出；需要一直高电平时，请选 13 位或更低。舵机信号不受影响，因为它只用到 5–10 % 的 duty（819 到 1638）。要产生 1.5 ms 的脉冲：

```text
pulse / period = 1.5 ms / 20 ms = 0.075
duty = 0.075 × 16384 = 1228.8
取整数: 1228
```

下面项目里的程序，在 `angleToDuty()` 中用的就是同一套整数运算：先把角度换算成微秒，再缩放到 duty。在电脑上运行这个函数，得到的正是下面这张表：

```text
angle   0 -> duty 819
angle  45 -> duty 1024
angle  90 -> duty 1228
angle 135 -> duty 1433
angle 180 -> duty 1638
```

注意这些值并不是完全等距的：819、1024、1228、1433、1638，相邻差分别是 205、204、205、205。这很正常。换算过程中每一步都是整数除法，余数被丢掉，于是这里少半格、那里少半格。14 位下一个 duty 步进是 20 ms / 16384 ≈ 1.22 µs，远高于普通舵机能分辨的精度，所以这点截断在实际使用中无关紧要。

供电是初学者最常出错的地方。普通舵机的商品页面很少标出堵转电流，所以要自己测量：把万用表拨到 10 A 档，串接在舵机的电源线上（第 1 个月，工作台），命令一个角度，分别在舵机转动时、静止保持时，以及——最多一两秒——用手挡住舵盘使它无法转到目标角度时（堵转情形）读取电流。把堵转读数与电源能提供的电流作比较。计算机的 USB 2.0 口标称 500 mA，而开发板的 3.3 V 稳压器还要给 ESP32 供电，所以两者都承受不了舵机的堵转电流：电压轨被拉低，ESP32 因欠压而复位。正确做法是用独立的 5–6 V 电源给舵机供电，把它的地接到 ESP32 的地，只把信号线接到 GPIO。3.3 V 的信号通常能被 5 V 舵机认成高电平，如果舵机比较特殊，查一下数据手册。

## 项目：用手机控制舵机

这是本课的练习任务，而且它故意选了 Uno 不做额外扩展就办不到的事：ESP32 提供一个很小的网页，实时显示传感器读数，你在手机上按按钮，舵机就动。手机和板子必须在同一个网络里。

接线：

- 舵机信号 → GPIO 18。
- 舵机 + → 外部 5 V 电源。
- 舵机 − → GND，与 ESP32 共地。
- 电位器两端 → 3.3 V 和 GND。
- 电位器中间抽头 → 经典 ESP32 用 GPIO 34，S3 用 GPIO 4。

<CodeSource path="examples/month-2/esp32/web_servo/web_servo.ino" />

```cpp
// ESP32 web servo: a phone on the same Wi-Fi sees a live reading
// and moves a hobby servo with three buttons.
#include <WiFi.h>
#include <WebServer.h>

const char *WIFI_SSID = "your-network";
const char *WIFI_PASS = "your-password";

const int SERVO_PIN = 18;
const int POT_PIN = 34;        // classic ESP32: GPIO 34 is on ADC1 (works with Wi-Fi on). ESP32-S3: use GPIO 4.
const int SERVO_HZ = 50;       // standard hobby servo frame: 20 ms
const int SERVO_BITS = 14;     // duty 0..2^14; S3 max: 16384 (100 %) not settable

WebServer server(80);
int servoAngle = 90;

// 0..180 degrees -> 1000..2000 us pulse -> LEDC duty value
uint32_t angleToDuty(int angle) {
  uint32_t us = 1000 + (uint32_t)angle * 1000 / 180;
  return us * (1UL << SERVO_BITS) / 20000;
}

void setServo(int angle) {
  servoAngle = constrain(angle, 0, 180);
  ledcWrite(SERVO_PIN, angleToDuty(servoAngle));
}

const char PAGE[] = R"HTML(<!doctype html>
<html><head><meta name="viewport" content="width=device-width,initial-scale=1">
<title>ESP32 servo</title></head>
<body style="font-family:sans-serif;text-align:center">
<h1>ESP32 servo</h1>
<p>Knob: <b id="mv">-</b> mV &middot; Servo: <b id="deg">-</b>&deg;</p>
<p><button onclick="go(0)">0&deg;</button>
<button onclick="go(90)">90&deg;</button>
<button onclick="go(180)">180&deg;</button></p>
<script>
function go(a){fetch('/servo?angle='+a);}
async function poll(){
  try{const r=await fetch('/reading');const j=await r.json();
  document.getElementById('mv').textContent=j.mv;
  document.getElementById('deg').textContent=j.angle;}catch(e){}
  setTimeout(poll,500);}
poll();
</script></body></html>)HTML";

void handleRoot() { server.send(200, "text/html", PAGE); }

void handleReading() {
  char json[48];
  snprintf(json, sizeof json, "{\"mv\":%lu,\"angle\":%d}",
           (unsigned long)analogReadMilliVolts(POT_PIN), servoAngle);
  server.send(200, "application/json", json);
}

void handleServo() {
  if (!server.hasArg("angle")) { server.send(400, "text/plain", "missing angle"); return; }
  setServo(server.arg("angle").toInt());
  server.send(200, "text/plain", "ok");
}

void setup() {
  Serial.begin(115200);
  ledcAttach(SERVO_PIN, SERVO_HZ, SERVO_BITS);   // Arduino-ESP32 core 3.x API
  setServo(90);

  WiFi.mode(WIFI_STA);
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  Serial.print("Connecting");
  while (WiFi.status() != WL_CONNECTED) {         // fine in setup(); never do this in loop()
    delay(250);
    Serial.print('.');
  }
  Serial.println();
  Serial.print("Open http://");
  Serial.println(WiFi.localIP());

  server.on("/", handleRoot);
  server.on("/reading", handleReading);
  server.on("/servo", handleServo);
  server.begin();
}

void loop() {
  server.handleClient();   // non-blocking: answers any waiting request and returns
}
```

按程序实际执行的顺序读一遍。`setup()` 先启动串口，用 `ledcAttach()` 把舵机引脚挂到 LEDC 上，再把舵机转到 90°。接着把 Wi-Fi 切到 station 模式——也就是让 ESP32 加入一个已有网络，而不是自己建热点——再用账号密码调用 `WiFi.begin()`。连接成功之前，`while` 循环一直打印小圆点。这种阻塞写法放在 `setup()` 里没问题，因为此时还没有别的事要干；放到 `loop()` 里就不行，那会把机器人整个冻住。

连上之后，`WiFi.localIP()` 返回路由器分配到的地址。串口会把这个地址打出来，你在手机浏览器里输入的就是它，别忘了前面的 `http://`。如果小圆点一直打下去，说明账号密码不对，或者网络不在覆盖范围内。

程序注册了三条路由。`/` 返回存在 `PAGE` 里的 HTML 页面；`/reading` 用 `snprintf()` 拼出一小段 JSON，里面有校准后的毫伏读数和当前舵机角度；`/servo?angle=...` 读取查询参数，限幅后转动舵机。网页里的 JavaScript 每 500 ms 请求一次 `/reading`，把数字写进两个带 id 的标签。三个按钮分别调用 `go(0)`、`go(90)`、`go(180)`，向对应的舵机地址发请求。

`loop()` 里只有一行 `server.handleClient()`。它检查有没有等待处理的请求，有就回应，然后立刻返回。正是这种非阻塞设计，让你之后还能用计时课上的 `millis()` 模式加入自己的传感器读取和控制代码。网页服务器不霸占 CPU，它只是每轮循环来取一小片时间。

`constrain(angle, 0, 180)` 是一道很小但很重要的护栏。一个格式错误的请求就可能发来 `angle=900`，常见来源是手机输入法的自动补全。没有限幅，脉宽会远远超出舵机的机械范围，舵机就会顶着限位咔咔作响。有了它，最坏情况也不过是 180°。

还有一个网络细节经常卡住人：**ESP32 的 Wi-Fi 只支持 2.4 GHz**。如果你的手机只连在 5 GHz 网络上，板子永远不会出现，密码再对也没用。多数家用路由器把两个频段用同一个名字发布、由路由器替你选；如果你家路由器把两个名字分开了，测试时让手机连 2.4 GHz 那个。

<Callout type="warn" title="别把 Wi-Fi 密码提交到 Git">
不要把真实的 Wi-Fi 名称和密码提交到 GitHub。把 `WIFI_SSID` 和 `WIFI_PASS` 放进单独的 `secrets.h`，把这个文件写进 `.gitignore`，仓库里只提交一个填着占位符的 `secrets.example.h`。[Git 与 GitHub 那一课](/zh/month/month-1/git-github)讲过忽略文件的作用，也讲过为什么即使后来删掉，历史记录里仍然留着秘密。
</Callout>

基础版本跑通之后，可以试这些扩展：

- 把三个按钮换成一个范围滑块，可以发送 0 到 180 之间的任意角度。
- 加上 mDNS，让页面用 `http://robot.local` 打开，不必记会变的 IP。
- 在 `loop()` 里加断线重连：发现 `WiFi.status()` 不再等于已连接，就重试，而不是重启整块板。
- 把电位器读数显示成数字，并用它直接控制舵机，再对比旋钮位置和命令角度是否一致。


## FreeRTOS 优先级、反转与中等任务

Arduino 的 `setup()` / `loop()` 已经跑在一个 <Term id="freertos-task">FreeRTOS 任务</Term> 里。当你需要不止一个速率——200 Hz 控制环、更慢的日志、Wi-Fi——就要按优先级创建任务。**FreeRTOS 编号：数字越大优先级越高**（`tskIDLE_PRIORITY` = 0，最低）。这和 Zephyr 的极性相反（见下文对照）。

### 为什么必须是三个任务

只用低、高两个任务，优先级反转很容易讲浅。低任务持有互斥量、高任务在上面阻塞时，若**没有别的就绪任务**，低任务会一直占用 CPU 做完临界区：高任务的等待只是这段剩余时间。**无界**反转需要一个**从不拿锁**的**中等**任务：高任务阻塞期间，中等任务抢占仍持锁的低任务，高任务就会被拖住，拖多久取决于中等任务跑多久。

因此玩具在**单核**上放了三个任务：

| 任务 | FreeRTOS 优先级 | 角色 |
| --- | --- | --- |
| `low` | 1 | 日志：持锁进入较长临界区 |
| `medium` | 2 | 后台： **从不**拿锁 |
| `high` | 3 | 控制：每个周期短暂需要锁 |

ESP-IDF 的 FreeRTOS 是带核心亲和性的 **SMP 双核**变体（`xTaskCreatePinnedToCore`，每核 idle/IPC 任务）——见 <Resource id="esp-idf-freertos-overview" />。本玩具刻意做成**单核**，好让反转时间线不被 SMP 调度打散。在 ESP32 上烧录真实 FreeRTOS 工程 **本页未运行**。

### 互斥量 vs 二值信号量

FreeRTOS 里有两个容易混用的原语（<Resource id="freertos-kernel-semphr" /> — FreeRTOS-Kernel 的 `semphr.h`）：

- `xSemaphoreCreateMutex()` — **有优先级继承**：更高优先级任务因该互斥量阻塞时，持有者的有效优先级会被抬高。
- `xSemaphoreCreateBinary()` — **没有**优先级继承。头文件写得很清楚，并指向互斥量作为带继承的替代。

经典坑就是把二值信号量当成互斥锁用。继承**限制**中等任务造成的等待；它**不会**消掉阻塞：高任务仍要等低任务做完临界区（本课不做优先级天花板断言）。

```python
#!/usr/bin/env python3
"""freertos_priority_toy.py: priority inversion with a medium task (stdlib).

Single-core fixed-priority preemptive scheduler in FreeRTOS numbering
(higher numeric priority runs first; tskIDLE_PRIORITY = 0 is lowest).
ESP-IDF FreeRTOS is an SMP dual-core variant with core affinity; this toy
is deliberately single-core so the inversion story is visible without SMP
scheduling. Real FreeRTOS on ESP32 and Zephyr builds are 本页未运行.

Three tasks share one mutex-guarded critical section:
  low     (prio 1)  logging — takes the mutex for a long stretch
  medium  (prio 2)  background — never takes the mutex
  high    (prio 3)  control — needs the mutex briefly each period

Unbounded inversion needs the medium task: without it, when high blocks on
the mutex held by low, low keeps the CPU (nothing else is ready at a higher
priority than low among non-blocked tasks), so high's wait is just low's
remaining critical-section time. With medium ready, medium preempts low and
high stays blocked for an unbounded medium stretch.

Arms (shared arrival noise):
  no_inheritance  lock is a binary-semaphore stand-in: no priority boost
  inheritance     lock is a mutex stand-in: holder inherits waiter's priority

FreeRTOS fact (kernel semphr.h): xSemaphoreCreateMutex() implements priority
inheritance; xSemaphoreCreateBinary() does not — using a binary semaphore as
a mutual-exclusion lock is the classic bug. Inheritance BOUNDS blocking by
the medium task; it does not eliminate the wait for the low task to finish
its critical section (no priority-ceiling claim here).

Zephyr polarity (prose only, docs.zephyrproject.org threads): lower number =
higher priority; negative priorities are cooperative. Toy stays FreeRTOS
numbering.

Metrics: high-task deadline misses; max inversion wait (ticks high spent
blocked while a medium ran).
usage: python3 freertos_priority_toy.py
"""
from __future__ import annotations

import random

SEED = 42
HORIZON = 400          # scheduler ticks
DT_MS = 1              # one tick = 1 ms of simulated time

# FreeRTOS-style priorities: higher number = higher priority.
P_LOW, P_MED, P_HIGH = 1, 2, 3

# Workloads (ticks of CPU needed per job).
LOW_CS = 18            # low's critical-section length while holding the lock
LOW_PERIOD = 80
MED_BURST = 12         # medium CPU burst (no lock)
MED_PERIOD = 25
HIGH_CS = 3            # high's short critical section
HIGH_PERIOD = 20
HIGH_DEADLINE = 20     # miss if response > this many ticks from release

# Shared arrival jitter (±ticks) applied identically to both arms.
ARRIVAL_JITTER = 2


class Scheduler:
    """Tiny single-core preemptive FP scheduler with one lock."""

    def __init__(self, inherit: bool, arrivals: list[tuple[int, int, int]]) -> None:
        self.inherit = inherit
        self.arrivals = arrivals  # (low_rel, med_rel, high_rel) jitter per period index
        self.lock_holder: str | None = None
        self.lock_waiters: list[str] = []
        # base priority / effective priority
        self.base = {"low": P_LOW, "medium": P_MED, "high": P_HIGH}
        self.eff = dict(self.base)
        self.ready: dict[str, int] = {}          # task -> remaining CPU this job
        self.blocked: set[str] = set()
        self.release_at = {"low": 0, "medium": 0, "high": 0}
        self.period_i = {"low": 0, "medium": 0, "high": 0}
        self.high_release_tick: int | None = None
        self.deadline_misses = 0
        self.max_inv_wait = 0
        self.cur_inv_wait = 0
        self.max_lock_wait = 0
        self.cur_lock_wait = 0
        self.high_jobs = 0
        self.high_responses: list[int] = []
        self.holding_cs_left = 0  # remaining CS work while holding lock

    def _prio(self, name: str) -> int:
        return self.eff[name]

    def _boost(self) -> None:
        """Priority inheritance: holder gets max(own, waiters' base)."""
        if not self.inherit or self.lock_holder is None:
            return
        holder = self.lock_holder
        boost = self.base[holder]
        for w in self.lock_waiters:
            boost = max(boost, self.base[w])
        self.eff[holder] = boost

    def _drop_boost(self) -> None:
        if self.lock_holder is None:
            self.eff = dict(self.base)
            return
        # reset non-holders; re-compute holder
        for n in self.eff:
            if n != self.lock_holder:
                self.eff[n] = self.base[n]
        self._boost()

    def _try_release(self, t: int) -> None:
        for name, period, work in (
            ("low", LOW_PERIOD, LOW_CS),
            ("medium", MED_PERIOD, MED_BURST),
            ("high", HIGH_PERIOD, HIGH_CS),
        ):
            if t < self.release_at[name]:
                continue
            if name in self.ready or name in self.blocked or name == self.lock_holder:
                # still running previous job; skip this release (overload)
                self.release_at[name] = t + period
                self.period_i[name] += 1
                continue
            # apply shared arrival jitter
            pi = self.period_i[name]
            jitter_triple = self.arrivals[pi % len(self.arrivals)]
            jitter = {"low": jitter_triple[0], "medium": jitter_triple[1],
                      "high": jitter_triple[2]}[name]
            # release now (jitter already baked into precomputed arrival offsets
            # relative to nominal; we just start the job)
            self.ready[name] = work
            if name == "high":
                self.high_release_tick = t
                self.high_jobs += 1
            self.release_at[name] = t + period + jitter
            self.period_i[name] += 1
            _ = jitter  # jitter shifts next release; first release at 0

    def _take_lock(self, name: str) -> bool:
        if self.lock_holder is None:
            self.lock_holder = name
            self.holding_cs_left = self.ready[name]
            self._boost()
            return True
        if self.lock_holder == name:
            return True
        # must wait
        if name not in self.lock_waiters:
            self.lock_waiters.append(name)
        self.blocked.add(name)
        if name in self.ready:
            # keep remaining work recorded in ready? move to blocked
            pass
        self._boost()
        return False

    def _give_lock(self) -> None:
        self.lock_holder = None
        self.holding_cs_left = 0
        # wake waiters in priority order
        self.lock_waiters.sort(key=lambda n: -self.base[n])
        woken = []
        while self.lock_waiters:
            w = self.lock_waiters.pop(0)
            self.blocked.discard(w)
            woken.append(w)
            # highest waiter takes the lock immediately
            self.lock_holder = w
            self.holding_cs_left = self.ready.get(w, HIGH_CS)
            break
        self._drop_boost()
        self._boost()

    def _pick(self) -> str | None:
        candidates = []
        for name, rem in self.ready.items():
            if rem <= 0:
                continue
            if name in self.blocked:
                continue
            # if someone else holds the lock and this task needs it:
            # low and high need the lock for their whole job in this toy;
            # medium never needs it.
            if name in ("low", "high"):
                if self.lock_holder is not None and self.lock_holder != name:
                    # try to take (will block)
                    if not self._take_lock(name):
                        continue
                elif self.lock_holder is None:
                    if not self._take_lock(name):
                        continue
            candidates.append(name)
        if not candidates:
            return None
        # highest effective priority wins; stable by name for ties
        candidates.sort(key=lambda n: (-self._prio(n), n))
        return candidates[0]

    def run(self) -> dict:
        for t in range(HORIZON):
            self._try_release(t)
            # inversion wait = high blocked WHILE medium runs (unbounded w/o PI)
            # lock wait = any tick high spends blocked on the lock (bounded by low CS under PI)
            high_blocked = "high" in self.blocked
            running = self._pick()
            # re-read blocked after _pick (which may have blocked high)
            high_blocked = "high" in self.blocked
            if high_blocked:
                self.cur_lock_wait += 1
                self.max_lock_wait = max(self.max_lock_wait, self.cur_lock_wait)
                if running == "medium":
                    self.cur_inv_wait += 1
                    self.max_inv_wait = max(self.max_inv_wait, self.cur_inv_wait)
                else:
                    self.cur_inv_wait = 0
            else:
                self.cur_inv_wait = 0
                self.cur_lock_wait = 0

            if running is None:
                continue

            # execute one tick
            self.ready[running] -= 1
            if running == self.lock_holder:
                self.holding_cs_left -= 1

            if self.ready[running] <= 0:
                # job done
                if running == "high" and self.high_release_tick is not None:
                    resp = t - self.high_release_tick + 1
                    self.high_responses.append(resp)
                    if resp > HIGH_DEADLINE:
                        self.deadline_misses += 1
                    self.high_release_tick = None
                if running == self.lock_holder:
                    self._give_lock()
                del self.ready[running]

        return {
            "arm": "inheritance" if self.inherit else "no_inheritance",
            "deadline_misses": self.deadline_misses,
            "high_jobs": self.high_jobs,
            "max_inversion_wait_ticks": self.max_inv_wait,
            "max_inversion_wait_ms": self.max_inv_wait * DT_MS,
            "max_lock_wait_ticks": self.max_lock_wait,
            "mean_high_response_ticks": (
                sum(self.high_responses) / len(self.high_responses)
                if self.high_responses else 0.0),
        }


def shared_arrivals() -> list[tuple[int, int, int]]:
    rng = random.Random(SEED)
    # enough for HORIZON / min_period
    n = HORIZON // 10 + 5
    out = []
    for _ in range(n):
        out.append((
            rng.randint(-ARRIVAL_JITTER, ARRIVAL_JITTER),
            rng.randint(-ARRIVAL_JITTER, ARRIVAL_JITTER),
            rng.randint(-ARRIVAL_JITTER, ARRIVAL_JITTER),
        ))
    return out


def main() -> None:

    rows = []
    for inherit in (False, True):
```

### Zephyr 极性（仅文字）

Zephyr 线程文档（<Resource id="zephyr-threads" />）写明：**数字越小优先级越高**，**负数**表示**协作式**线程。FreeRTOS 在数轴上相反。移植时不翻转优先级表是真实 bug；本课玩具保持 FreeRTOS 编号，**不构建 Zephyr**（本页未运行）。

不要把第三方 RTOS 周期数博客当成 ESP32 上的站内实测。玩具只报告课内工作负载下的 deadline miss 与等待 tick，并不宣称「FreeRTOS 一定比 Zephyr 快」。

## ESP32 的 Light-sleep 与 Deep-sleep 能耗

<Resource id="idf-sleep-modes" />

ESP-IDF 的 **Sleep Modes** 页面介绍了两种主要省电模式（以文档为准）。**Light-sleep** 时，数字外设、大部分 RAM 和 CPU 被时钟门控并降低供电电压；退出后它们恢复运行，**内部状态保留**。**Deep-sleep** 时，CPU、大部分 RAM 以及所有由 APB 时钟驱动的数字外设**断电**；只剩 RTC 控制器、ULP 协处理器和 RTC FAST / RTC SLOW 内存保持供电，从 Deep-sleep 唤醒时先运行唤醒桩，再加载应用。唤醒源可以**组合**，包括 RTC 定时器、触摸、ext0 / ext1（仅 RTC IO）、ULP 协处理器、Light-sleep 下的 GPIO 唤醒（任意 IO，RTC 或数字均可），以及 Deep-sleep 下的 GPIO 唤醒（仅 VDD3P3_RTC 电源域的引脚）。两种模式下 Wi-Fi 和蓝牙连接都**不保持**。我们读到的正文**没有休眠电流表，也没有唤醒延迟数值**，所以下面所有电流和唤醒代价都是**声明的玩具参数**，不是数据手册数值。

这一节**不是**上面的 ADC 衰减 / Wi-Fi 下的 ADC2 内容，也**不是**本页的 FreeRTOS 优先级玩具；它也**不是** FreeRTOS 的 tickless 空闲。

<Formula label="每周期电荷，Light-sleep">Q_B(g) = I_ACTIVE (T_WAKE_LIGHT + WORK) + I_LIGHT (g − T_WAKE_LIGHT − WORK)</Formula>

<Formula label="每周期电荷，Deep-sleep">Q_C(g) = I_BOOT T_BOOT_DEEP + I_ACTIVE WORK + I_DEEP (g − T_BOOT_DEEP − WORK)</Formula>

**手算例题，已由 toy 打印。** 按声明参数，周期为 g 的一次唤醒循环消耗 A = 40.0 × g、B = 1.9992 + 0.80 × g、C = 16.9965 + 0.01 × g（单位 mA·s；C 的公式只在 g ≥ T_BOOT_DEEP + WORK = 0.350 s 时成立）。令它们相等得到盈亏平衡间隔，**当且仅当 g > 0.4250 s** 时 Deep-sleep 的电荷严格少于常开，**当且仅当 g > 18.9839 s** 时严格少于 Light-sleep；取等号时两者打平。g = 60.00 s 时玩具打印 A = 2400.0000、B = 49.9992、C = 17.5965 mA·s/周期。g = 0.25 s 时 C 的公式**不成立**，因为 Deep-sleep 在下一个事件到来之前完不成 0.300 s 的启动，所以要看下面的事件驱动运行结果。

**这里没有积分步长。** 这个 toy 只把事件之间的电流 × 时间加起来；没有微分方程，也没有步长稳定性判据。

### 公平设置

`esp32_light_deep_sleep_toy.py` 是**合成**的，只用标准库。**模型假设:** 芯片一空闲就立即进入休眠（没有进入开销）；芯片醒着（工作或启动中）时到达的事件排队处理；休眠期间到达、且来源**没有**被设为唤醒源的事件算作**漏掉**；每个处理的事件在 I_ACTIVE 下花 WORK = 0.050 s。声明的玩具电流：I_ACTIVE = 40.0 mA，I_LIGHT = 0.80 mA，I_DEEP = 0.01 mA，I_BOOT = 50.0 mA；声明的唤醒代价：T_WAKE_LIGHT = 0.001 s，T_BOOT_DEEP = 0.300 s。这些都不是从 Espressif 引来的。两个休眠臂里 Wi-Fi 都视为断开：每次唤醒记一次掉线，重连能耗**没有**建模。

| 臂 | 休眠策略 |
|---|---|
| A_active | 从不休眠 |
| B_light | 空闲时 Light-sleep；RAM 保留；定时器、RTC-IO GPIO 和数字 GPIO 都能唤醒 |
| C_deep | 空闲时 Deep-sleep；每次唤醒 RAM 丢失，RTC SLOW 计数保留；只有定时器和 RTC-IO GPIO 能唤醒 |

**共用随机数:** 每个（情形, 种子）的事件时间线只抽一次，三臂共享。三臂**只**在休眠模式、唤醒源和唤醒代价上不同。五个种子。指标是窗口内的平均电流、漏掉的事件、唤醒次数，以及从事件到开始处理的平均时间，按种子报 mean±sd。状态检查确认 B 保留 RAM 计数、C 只保留 RTC SLOW 计数。

| 情形 | 时间线 | 预先声明 |
|---|---|---|
| long_idle | RTC 定时器约每 60 s 一次，窗口 3600 s | C 相对 A（也相对 B）**稳定地**能耗最低 |
| high_wake_rate | RTC-IO GPIO 事件，平均间隔 0.25 s，加定时器，窗口 600 s | 因为唤醒开销，C 相对 A 可能**接近打平或输**，并输给 B；**保留** |
| missed_wake_source | 定时器约每 60 s 一次，加上只接数字 GPIO 的事件（平均间隔 30.00 s） | C **稳定地**漏事件，因为那根引脚不是 Deep-sleep 唤醒源；**保留** |

0.25 s 的平均间隔是在首次运行前选的，让它落在手算的 0.4250 s（C 对 A 的盈亏平衡）之下。

```python
"""ESP32 Light-sleep vs Deep-sleep energy over a shared event timeline.

Synthetic charge bookkeeping, stdlib only.  Not esp_light_sleep_start() or
esp_deep_sleep_start() on a board, not a power-analyser capture, not the
FreeRTOS scheduler toy and not the ADC section.  Real ESP32: 本页未运行.
ESP-IDF Sleep Modes statements 以文档为准.

What the ESP-IDF Sleep Modes page says (and what this toy keeps):
  Light-sleep: digital peripherals, most RAM and the CPUs are clock-gated and
    their supply is reduced; on exit their internal state is preserved.
  Deep-sleep: CPUs, most RAM and APB-clocked digital peripherals are powered
    off; RTC controller, ULP, RTC FAST and RTC SLOW memory can stay on.  On a
    Deep-sleep wake the chip runs the wake stub and then loads the app.
  Wakeup sources can be combined.  ext0 / ext1 use RTC IOs only; GPIO wakeup
    from Light-sleep works on any IO; Deep-sleep GPIO wakeup is limited to
    RTC-domain pins.  Wi-Fi / Bluetooth connections are not maintained in
    either sleep mode.
The page body we read gives no sleep-current or wake-latency table, so every
current and wake cost below is a declared toy parameter, printed, and NOT a
datasheet value.

Common random numbers: one event timeline per (regime, seed), shared by every
arm.  Arms:
  A_active : never sleeps (I_ACTIVE the whole window)
  B_light  : Light-sleep whenever idle; T_WAKE_LIGHT wake cost; RAM kept;
             wake sources timer + any GPIO
  C_deep   : Deep-sleep whenever idle; T_BOOT_DEEP wake (stub + app load) at
             I_BOOT; RAM lost on every wake, RTC SLOW counter kept;
             wake sources timer + RTC-IO GPIO only
The arms differ only in the sleep mode (and its wake sources and costs).
An event that arrives while the chip is awake is queued and served; an event
on a source that is not enabled while the chip sleeps is missed.  Sleep is
entered immediately when idle (no entry overhead).  Wi-Fi is down in both
sleep arms: each wake counts one link drop, but reconnect energy is NOT
modelled.  No integration step: event-driven bookkeeping of I x t, no ODE.

Regimes and parameters were written before the first run:
  long_idle          : RTC timer wake every ~60 s, nothing else
                       - C consistent lowest energy vs A (and vs B); keep
  high_wake_rate     : RTC-IO GPIO events, mean gap 0.25 s (chosen below the
                       hand-calculated C-vs-A break-even before the run)
                       - C may near-tie or LOSE to A, and loses to B; keep
  missed_wake_source : timer every ~60 s plus events on a digital-only GPIO
                       - C consistent miss (not an enabled Deep-sleep wake
                       source); B catches them; keep
"""
import math
import random

SEEDS = (0, 1, 2, 3, 4)
NUM_ZERO = 1e-9

# Declared model parameters, written before the first run.  Toy values, not
# datasheet mA / uA, not measured here.

I_LIGHT = 0.8         # mA, Light-sleep floor (toy)
I_DEEP = 0.01         # mA, Deep-sleep floor (toy)
I_BOOT = 50.0         # mA, Deep-sleep wake: stub + app load + re-init (toy)
T_WAKE_LIGHT = 0.001  # s, Light-sleep wake cost at I_ACTIVE (toy)
T_BOOT_DEEP = 0.300   # s, Deep-sleep wake cost at I_BOOT (toy)
WORK = 0.050          # s, work per served event at I_ACTIVE
V_SUPPLY = 3.3        # V, only to convert charge to energy

ARMS = ("A_active", "B_light", "C_deep")
WAKE_SOURCES = {
    "A_active": ("timer", "rtc_gpio", "digital_gpio"),
    "B_light": ("timer", "rtc_gpio", "digital_gpio"),
    "C_deep": ("timer", "rtc_gpio"),
}
REGIMES = {
    "long_idle": {"window": 3600.0, "timer": 60.0, "gpio_gap": None, "gpio_src": None},
    "high_wake_rate": {"window": 600.0, "timer": 60.0, "gpio_gap": 0.25, "gpio_src": "rtc_gpio"},
    "missed_wake_source": {"window": 3600.0, "timer": 60.0, "gpio_gap": 30.0, "gpio_src": "digital_gpio"},
}
TIMER_JITTER = 0.5    # s, +/- uniform on each timer period


def shared_timeline(regime, seed):
    """Common random numbers: one event list used by every arm."""
    rng = random.Random(f"{regime}/{seed}")
    cfg = REGIMES[regime]
    ev = []
    t = 0.0
    while True:
        t += cfg["timer"] + rng.uniform(-TIMER_JITTER, TIMER_JITTER)
        if t >= cfg["window"]:
            break
        ev.append((t, "timer"))
    if cfg["gpio_gap"]:
        t = 0.0
        while True:
            t += rng.expovariate(1.0 / cfg["gpio_gap"])
            if t >= cfg["window"]:
                break
            ev.append((t, cfg["gpio_src"]))
    ev.sort()
    return ev


def simulate(arm, events, window, i_boot=I_BOOT, t_boot=T_BOOT_DEEP):
    charge = 0.0          # mA*s
    busy_until = 0.0      # chip awake until this time; idle afterwards
    served = missed = wakes = 0
    lat = []
    ram = rtc = 0         # RAM counter (lost in Deep-sleep) and RTC SLOW counter
    ram_ok = True
    if arm == "A_active":
        for t, _src in events:
            start = max(t, busy_until)
            lat.append(start - t)
            busy_until = start + WORK
            served += 1
            ram += 1
            rtc += 1
        charge = I_ACTIVE * max(window, busy_until)
        return {"charge": charge, "served": served, "missed": 0, "wakes": 0,
                "lat": sum(lat) / len(lat), "ram": ram, "rtc": rtc, "ram_ok": ram == served}
    i_sleep = I_LIGHT if arm == "B_light" else I_DEEP
    for t, src in events:
        if t > busy_until:  # strictly after the last work ended: the chip is asleep
            charge += i_sleep * (t - busy_until)
            if src not in WAKE_SOURCES[arm]:
                missed += 1
                busy_until = t  # still asleep; sleep charge already counted up to t
                continue
            wakes += 1
            if arm == "B_light":
                charge += I_ACTIVE * T_WAKE_LIGHT
                start = t + T_WAKE_LIGHT
            else:
                charge += i_boot * t_boot
                start = t + t_boot
                ram = 0  # RAM powered off in Deep-sleep
        else:              # awake (working or booting): queue, any source is seen
            start = busy_until
        lat.append(start - t)
        charge += I_ACTIVE * WORK
        busy_until = start + WORK
        served += 1
        ram += 1
        rtc += 1
    if busy_until < window:
        charge += i_sleep * (window - busy_until)
    ram_ok = (ram == served) if arm == "B_light" else (ram <= served)
    return {"charge": charge, "served": served, "missed": missed, "wakes": wakes,
            "lat": (sum(lat) / len(lat)) if lat else 0.0, "ram": ram, "rtc": rtc, "ram_ok": ram_ok}


def mean_sd(xs):
    mu = sum(xs) / len(xs)
    return mu, math.sqrt(sum((x - mu) ** 2 for x in xs) / (len(xs) - 1))


def num(x):
    if x != 0.0 and abs(x) < 5e-4:
        return f"{x:.3e}"
    return f"{x:.4f}"


def sign_note(diffs, m):
    n, opp, zero = len(diffs), sum(1 for d in diffs if d * m < 0), sum(1 for d in diffs if d == 0)
    if opp == 0 and zero == 0:
        return f"same sign on all {n} seeds"
    if opp == 0:
        return f"no seed has the opposite sign, {zero} of {n} equal"
    note = f"{opp} of {n} seeds {'has' if opp == 1 else 'have'} the opposite sign"
    return note + (f", {zero} of {n} equal" if zero else "")


def fmt_pair(m, s):
    return f"{num(m)}+-{num(s)}"


def verdict(xa, xb):
    diffs = [a - b for a, b in zip(xa, xb)]
    if all(d == 0.0 for d in diffs):
        return "0.0000+-0.0000: tie: identical on every seed"
    m, s = mean_sd(diffs)
    if abs(m) < NUM_ZERO and s < NUM_ZERO:
        return f"{fmt_pair(m, s)}: numerically zero (floating-point residue), effectively a tie"
    if abs(m) <= s:
        label = "near-tie / small gap, within seed noise (|m| <= sd)"
    elif abs(m) < 0.2 * min(abs(mean_sd(xa)[0]), abs(mean_sd(xb)[0])):
        label = "small but consistent gap, not a tie (|m| > sd)"
    else:
        label = "clear gap, not a tie (|m| > sd)"
    return f"{fmt_pair(m, s)}: {label}; {sign_note(diffs, m)}"


def per_cycle_charge(arm, gap, i_boot=I_BOOT, t_boot=T_BOOT_DEEP):
    """Hand calculation: charge (mA*s) for one wake cycle of period gap."""
    if arm == "A_active":
        return I_ACTIVE * gap
    if arm == "B_light":
        return I_ACTIVE * (T_WAKE_LIGHT + WORK) + I_LIGHT * (gap - T_WAKE_LIGHT - WORK)
    return i_boot * t_boot + I_ACTIVE * WORK + I_DEEP * (gap - t_boot - WORK)


def breakeven(i_boot=I_BOOT, t_boot=T_BOOT_DEEP):
    # C < A  iff  gap > g_ca ;  C < B  iff  gap > g_cb  (strict; equality is a tie)
    g_ca = (i_boot * t_boot + I_ACTIVE * WORK - I_DEEP * (t_boot + WORK)) / (I_ACTIVE - I_DEEP)
    g_cb = ((i_boot * t_boot + I_ACTIVE * WORK - I_DEEP * (t_boot + WORK))
            - (I_ACTIVE * (T_WAKE_LIGHT + WORK) - I_LIGHT * (T_WAKE_LIGHT + WORK))) / (I_LIGHT - I_DEEP)
    return g_ca, g_cb


def run_regime(regime, i_boot=I_BOOT, t_boot=T_BOOT_DEEP):

    return res
```

**看过结果后做的选择。** 没有。电流、唤醒代价、窗口、0.25 s 间隔以及下面两个替代都在首次运行前写定。high_wake_rate 上同一组种子的替代：I_BOOT = 40.0 mA（等于 I_ACTIVE）把 C 对 A 的盈亏平衡移到 g > 0.3500 s，成对 C−A 为 -14.2824±0.1689；T_BOOT_DEEP = 0.100 s 把它移到 g > 0.1750 s，成对 C−A 为 -20.2624±0.0965。两者都是有利于 C 的**明显差距，不是打平**；都没有采用，默认启动代价不变。

本页**不宣布普遍赢家**。长时间空闲有利于 Deep-sleep，高唤醒率会侵蚀它的优势并让 Light-sleep 胜出，而 Deep-sleep 会漏掉它无法被唤醒的引脚上的事件。真实 ESP32 以及板上的 `esp_deep_sleep_start()` 均**本页未运行**。

**180 分钟安排:** 30 分钟读 ESP-IDF Sleep Modes 页面（模式、唤醒源、Wi-Fi）；30 分钟手算每周期电荷和两个盈亏平衡间隔；50 分钟运行玩具，读三种情形和状态检查；40 分钟固定种子对照打印的 I_BOOT = 40.0 mA 与 T_BOOT_DEEP = 0.100 s 替代；30 分钟做练习。

2. 从 `shared_timeline` 说明：对给定情形和种子，A、B、C 看到的是同一组事件。

**本课要点**

- ESP32-S3：双核 Xtensa LX7，主频 240 MHz，512 KB SRAM，Wi-Fi 与 BLE 5（无蓝牙经典），原生 USB：时钟是 Uno 的 15 倍，RAM 是 256 倍。
- 上传：添加开发板管理器网址，选择 ESP32S3 Dev Module，为原生口的 `Serial` 启用 USB CDC On Boot，连接不上时用 BOOT + RESET。
- DevKitC-1 只有一颗可寻址 RGB LED，位于 GPIO 38（v1.1）或 GPIO 48（v1.0），用 `rgbLedWrite()` 驱动。
- 3.3 V 逻辑，不耐 5 V：1 kΩ / 2 kΩ 分压得到 3.333 V，标称比 VIH = 2.475 V 高 0.86 V。
- ESP32-S3 要留空的引脚：strapping 0、3、45、46；USB 19、20；UART0 43、44；Flash 与 PSRAM 26–32（八线 PSRAM 还有 35–37）；ADC1 是 GPIO 1–10。
- ADC：12 位，默认 `ADC_11db` 量程约 0–3.1 V；用 `analogReadMilliVolts()` 读电压。
- LEDC 舵机脉冲：duty = pulse / period × 2^bits；50 Hz、14 位下 1.5 ms 对应 1228。
- 舵机用独立的 5–6 V 电源供电并共地，并测量它们的堵转电流。
- FreeRTOS：数字越大优先级越高；无界反转需要中等任务；互斥量有继承、二值信号量没有；继承只限制阻塞。
- ESP-IDF FreeRTOS 是 SMP 双核；本课调度玩具是单核。Zephyr：数字越小优先级越高（仅文字）。
- ESP32 休眠：在共享事件时间线和声明的玩具电流（不是数据手册数值）下，长时间空闲时 Deep-sleep 电流最低（成对 C−A -39.7086±0.0026 mA，明显，5/5）；平均唤醒间隔 0.25 s 时 Deep-sleep 输给 Light-sleep（成对 C−B 21.1306±0.2356 mA，明显，5/5，保留），并会漏掉它无法被唤醒的引脚上的事件（成对 C−B missed 122.0000±10.3199，明显，5/5）——合成模型，不是真板实测。

## Pick the right communication pattern

<Term id="ros-node">A node</Term> is one program with one job. The whole ROS 2 style is to give each job its own node — one reads the lidar, one filters the readings, one decides where to drive — and then let them exchange messages instead of calling each other directly. That last part is what makes a system replaceable: as long as the messages keep the same shape, you can rewrite, restart or move any node without touching the others.

Nodes talk in three patterns, and most of the design work in ROS 2 is choosing between them.

| Pattern | Shape | Use it for | Example in this lesson |
| --- | --- | --- | --- |
| <Term id="topic">Topic</Term> | one-way stream, many publishers and subscribers, nobody waits | continuous data: sensor readings, images, velocity commands, odometry | /raw, /filtered, /summary |
| <Term id="service">Service</Term> | request → one reply, the caller waits | quick questions and settings that finish at once | /set_alpha |
| <Term id="action">Action</Term> | goal → stream of feedback → result, can be cancelled | anything that takes time: drive 2 m, move an arm, collect N samples | /collect |

Once you have that table in your head, the choice is usually obvious, and it is worth saying out loud as a rule of thumb:

- If it flows continuously — sensor readings, images, wheel speeds, odometry — use a **topic**. Nobody is waiting, and missing a message is acceptable.
- If it is a question with one immediate answer — read a setting, reset a counter, ask a node to switch mode — use a **service**. The caller waits for the reply, so the work has to be quick.
- If it takes longer than about a second, sends progress along the way, or might need stopping — drive two metres, move an arm, collect a hundred samples — use an **action**.

The two common mistakes both come from mixing these up. Using a service for something slow freezes the caller: it is blocked inside the call and cannot cancel, so a ten-second service looks exactly like a hung program. Using a topic for a command that must be acknowledged means the command can be dropped and nobody notices. If the work finishes in the same instant the request arrives, a service; if it drains your patience, an action.

There is a fourth thing, and it is not a way to send data at all: **parameters**. A parameter is a named setting that lives inside a node, declared with a default and then readable and changeable from outside. When you run `ros2 param set` you are not publishing anything; under the hood ROS 2 calls a service that every node is given for free, which is why parameters behave like settings and not like messages. They are how you tune a node without recompiling it.

Here is the system this lesson builds. Read it as a pipeline: readings enter on the left, statistics leave on the right, and two side channels control and collect.

<Diagram id="ros2-graph-system" />

The sensor publishes raw readings on `/raw`. The filter, written in C++, smooths each reading and republishes it on `/filtered`. The aggregator listens on `/filtered` and publishes a statistics message on `/summary`. The config node sits off to the side: when you call its `/set_alpha` service it validates the new smoothing factor and pushes it into the filter's `alpha` parameter through that node's own parameter service — the arrow labelled `set_parameters` in the diagram. The aggregator also runs a `/collect` action, so a client can ask it to gather a number of readings, watch feedback arrive, and cancel the job if it changes its mind. Four nodes, three patterns, one graph, and no hardware anywhere.

## Your own interfaces

Messages are typed. A topic does not carry an anonymous lump of bytes; it carries a message of a specific type, and both ends must agree on that type before a single message moves. The standard packages cover a surprising amount: `std_msgs` has plain values like `String` and `Float64`, `sensor_msgs` has `Image`, `LaserScan` and `Imu`, and `geometry_msgs` has `Twist`, `Pose` and `Point`. But a robot of your own soon needs fields nobody standardised — the readings from a particular sensor, the summary you want to compute — and then you write your own.

Your interfaces live in their own package. That package is built with CMake even if every node that uses it is written in Python, because generating message code is a code-generation step rather than a Python step; making it a CMake package is what lets any package, in any language, depend on it. In this lesson the interface package is called `m4_interfaces`, and both node packages depend on it.

Four files define our vocabulary. Each is a short text file with its own small grammar.

<CodeSource path="examples/month-4/ros2-graph/m4_interfaces/msg/Reading.msg" />

```text
# One sample from a sensor.
std_msgs/Header header   # stamp = when it was measured, frame_id = where
string sensor_id
float64 value
```

<CodeSource path="examples/month-4/ros2-graph/m4_interfaces/msg/Summary.msg" />

```text
# Statistics over the last `count` filtered readings.
uint32 count
float64 mean
float64 minimum
float64 maximum
```

<CodeSource path="examples/month-4/ros2-graph/m4_interfaces/srv/SetAlpha.srv" />

```text
# Ask the configuration node to change the filter's smoothing factor.
float64 alpha    # 0 < alpha <= 1; smaller = smoother but slower
---
bool accepted
string message
```

<CodeSource path="examples/month-4/ros2-graph/m4_interfaces/action/Collect.action" />

```text
# Collect a number of filtered readings and report their mean.
uint32 samples       # goal: how many readings to collect
---
uint32 received      # result
float64 mean
---
uint32 received      # feedback, sent after every reading
float64 latest
```

Look at the shapes and the three file types fall out. A `.msg` is simply a list of typed fields, one per line, written as `type name`. A `.srv` has two halves separated by a line of three dashes: everything above is the request, everything below is the response. An `.action` has three halves separated by two such lines: goal, then result, then feedback. That is the whole grammar, and once you can read it you can read almost any interface in ROS 2.

`std_msgs/Header` deserves a moment. It is the standard first field of any sensor message, and it carries two things: a timestamp called `stamp` (the moment the measurement was taken) and a frame name called `frame_id` (the coordinate frame the value belongs to). The timestamp lets a later node reason about delays; the frame name is how the value gets attached to a physical place on the robot. Frames do not matter yet — Lesson 3 is where they become real — but put a Header in every sensor message from the start, because adding one later means changing every node that touches the type. Field names are `lower_snake_case`; file names are `CamelCase`, which is why the file is `Reading.msg` and the field is `sensor_id`.

Generating the code is the job of the package's build file.

<CodeSource path="examples/month-4/ros2-graph/m4_interfaces/CMakeLists.txt" />

```cmake
cmake_minimum_required(VERSION 3.10)
project(m4_interfaces)

find_package(ament_cmake REQUIRED)
find_package(rosidl_default_generators REQUIRED)
find_package(std_msgs REQUIRED)

# Generate C++ and Python code for every interface listed here.
rosidl_generate_interfaces(${PROJECT_NAME}
  "msg/Reading.msg"
  "msg/Summary.msg"
  "srv/SetAlpha.srv"
  "action/Collect.action"
  DEPENDENCIES std_msgs
)

ament_export_dependencies(rosidl_default_runtime)
ament_package()
```

`rosidl_generate_interfaces` is the command that turns those text files into C++ headers and Python modules, and every interface you want has to be listed — miss one and its type simply does not exist. The `DEPENDENCIES std_msgs` line tells the generator that our messages reference `std_msgs/Header`, so it must look there while generating. `ament_export_dependencies(rosidl_default_runtime)` makes the runtime support available to packages that depend on us.

In `package.xml` a few lines matter, and they are easy to get wrong. Add a `buildtool_depend` on `rosidl_default_generators` (the generator), a `depend` on both `std_msgs` and `action_msgs` (the standard packages our messages build on), and an `exec_depend` on `rosidl_default_runtime` (needed when the generated code actually runs). Then add the group line `<member_of_group>rosidl_interface_packages</member_of_group>`. Forgetting that last line is the classic "it builds but the type is not found" error: the code is generated and installed correctly, but ROS never learns that this package provides interfaces, so `ros2 interface show` and other packages cannot find the types.

## Topics

### A publisher in Python

A topic needs someone to publish and someone to subscribe. The simplest sensor to start with is a node that generates synthetic readings: it needs no hardware, and its output is known exactly.

<CodeSource path="examples/month-4/ros2-graph/m4_graph/m4_graph/sensor_node.py" />

```python
"""Sensor publisher: a fake temperature sensor on /raw (no hardware needed).

The values are a slow wave plus noise from a fixed random seed, so every run publishes
the same sequence of numbers."""
import math
import random

import rclpy
from rclpy.executors import ExternalShutdownException
from rclpy.node import Node

from m4_interfaces.msg import Reading


class SensorNode(Node):
    def __init__(self):
        super().__init__('sensor_node')
        self.rate = self.declare_parameter('rate', 5.0).value          # Hz
        self.sensor_id = self.declare_parameter('sensor_id', 'temp0').value
        self.pub = self.create_publisher(Reading, 'raw', 10)
        self.rng = random.Random(7)
        self.k = 0
        self.create_timer(1.0 / self.rate, self.tick)
        self.get_logger().info(f'publishing /raw at {self.rate:.1f} Hz')

    def tick(self):
        msg = Reading()
        msg.header.stamp = self.get_clock().now().to_msg()
        msg.header.frame_id = 'sensor_link'
        msg.sensor_id = self.sensor_id
        msg.value = 21.0 + 0.5 * math.sin(2 * math.pi * self.k / 50) + self.rng.gauss(0, 0.2)
        self.pub.publish(msg)
        self.k += 1


def main():
    rclpy.init()
    node = SensorNode()
    try:
        rclpy.spin(node)
    except (KeyboardInterrupt, ExternalShutdownException):
        pass
    finally:
        node.destroy_node()
        rclpy.try_shutdown()
```

Two lines do most of the work of making this node configurable. `declare_parameter('rate', 5.0)` gives the node a setting named `rate` with a default of five; `.value` reads it back immediately. From now on a launch file or a YAML file can override that default without a single edit to this file. The header is filled in on every message: `get_clock().now()` gives the node's current time, and `.to_msg()` converts it to the header's time type; `frame_id` is set to `sensor_link`, a name that means nothing yet but will mean a lot in Lesson 3.

The value itself is deliberately boring: a slow sine wave around 21 °C with amplitude 0.5 °C, one cycle every 50 samples (10 s at the default 5 Hz `rate`), plus Gaussian noise with σ = 0.2 °C. The noise comes from `random.Random(7)`, a random generator started from a fixed seed. That is a small decision with a large payoff — a fixed seed means every run produces the same sequence of numbers, which is exactly what you want from a test signal. When a filter behaves strangely you can reproduce the exact input that caused it, instead of chasing a signal that was different last time.

### A filter in C++

The processing node is written in C++. The concepts are identical to the Python node, only the syntax and the compile step change; the month's milestone asks for nodes in both languages, and seeing the same ideas in two syntaxes is the quickest way to tell the concepts apart from the language.

<CodeSource path="examples/month-4/ros2-graph/m4_graph_cpp/src/filter_node.cpp" />

```cpp
// Processing node in C++: smooth /raw readings with an exponential moving average
// and publish them on /filtered. The smoothing factor is the parameter "alpha".
#include <memory>
#include <string>
#include <vector>

#include "m4_interfaces/msg/reading.hpp"
#include "rclcpp/rclcpp.hpp"

using m4_interfaces::msg::Reading;

class FilterNode : public rclcpp::Node
{
public:
  FilterNode()
  : Node("filter_node")
  {
    alpha_ = declare_parameter("alpha", 0.2);   // default; a launch file or YAML can override it
    // Reject bad values before they are applied (ros2 param set prints the reason).
    param_cb_ = add_on_set_parameters_callback(
      [this](const std::vector<rclcpp::Parameter> & params) {
        rcl_interfaces::msg::SetParametersResult result;
        result.successful = true;
        for (const auto & p : params) {
          if (p.get_name() == "alpha") {
            double a = p.as_double();
            if (a <= 0.0 || a > 1.0) {
              result.successful = false;
              result.reason = "alpha must be in (0, 1]";
            } else {
              alpha_ = a;
              RCLCPP_INFO(get_logger(), "alpha is now %.2f", alpha_);
            }
          }
        }
        return result;
      });
    pub_ = create_publisher<Reading>("filtered", 10);
    sub_ = create_subscription<Reading>(
      "raw", 10, [this](const Reading & msg) {on_reading(msg);});
    RCLCPP_INFO(get_logger(), "filtering /raw -> /filtered, alpha %.2f", alpha_);
  }

private:
  void on_reading(const Reading & msg)
  {
    // y = y + alpha * (x - y); the first reading starts the filter.
    estimate_ = have_estimate_ ? estimate_ + alpha_ * (msg.value - estimate_) : msg.value;
    have_estimate_ = true;
    Reading out = msg;          // keep the header and sensor_id
    out.value = estimate_;
    pub_->publish(out);
  }

  double alpha_;
  double estimate_ = 0.0;
  bool have_estimate_ = false;
  rclcpp::Publisher<Reading>::SharedPtr pub_;
  rclcpp::Subscription<Reading>::SharedPtr sub_;
  rclcpp::node_interfaces::OnSetParametersCallbackHandle::SharedPtr param_cb_;
};

int main(int argc, char ** argv)
{
  rclcpp::init(argc, argv);
  rclcpp::spin(std::make_shared<FilterNode>());
  rclcpp::shutdown();
  return 0;
}
```

The smoothing is an exponential moving average, and it is worth understanding because it is the same idea behind every "smooth this noisy signal" line you will write for the rest of the course. Stepping back to plain symbols, the update is:

```text
y ← y + α × (x − y)
```

where `x` is the new reading, `y` is the running estimate, and `α` (alpha) is a number between 0 and 1. In words: each new reading pulls the estimate a fraction `α` of the way towards it. A small `α` barely moves the estimate, so the output is smooth but lags the input; a large `α` follows the input quickly but lets more noise through; `α = 1` is no filtering at all, just copying the reading. The first reading has no estimate to smooth, so `have_estimate_` is used to seed the filter with it.

**Worked example**: the estimate is 21.00 °C and a new reading of 22.00 °C arrives.

```text
α = 0.2:  y = 21.00 + 0.2 × (22.00 − 21.00) = 21.00 + 0.20 = 21.20
α = 0.5:  y = 21.00 + 0.5 × (22.00 − 21.00) = 21.00 + 0.50 = 21.50
α = 1.0:  y = 21.00 + 1.0 × (22.00 − 21.00) = 21.00 + 1.00 = 22.00   (no filtering)
```

That is the whole arithmetic. Smaller α means the estimate moves less in one step, which is exactly what "smoother but slower" means.

The parameter callback is the second idea in this node, and it decides whether a change to the node's own settings is accepted: `add_on_set_parameters_callback` installs a function that runs every time someone tries to change a parameter, and if it returns `successful = false` with a reason, the change is refused before it takes effect. Here any `alpha` outside `(0, 1]` is rejected. This is a real pattern you will use constantly: a node that validates its own settings so a mistyped command cannot quietly corrupt its behaviour.

The subscription is the last piece. `create_subscription<Reading>("raw", 10, lambda)` says "call this function for each `Reading` on `raw`", and the lambda simply forwards to `on_reading`. Inside, `Reading out = msg;` copies the incoming message — including its header and `sensor_id` — before overwriting only `value`. That copy is deliberate: the timestamp of the original measurement now travels on with the filtered value, so a downstream node can still tell when the reading was taken, not when it was smoothed.

A C++ node needs a build file too, and it has one line that matters more than the rest.

## Services and parameters

Parameters can reach a node from three places, and knowing all three is what makes a node feel finished. The first is the default in `declare_parameter`, which is what you already saw. The second is a YAML file loaded at start, which lets you set up a whole graph's worth of settings without typing them every time. The third is a runtime change, either with `ros2 param set` or by calling the node's `set_parameters` service — which is what our config node does.

The YAML file is small, and its shape is the whole lesson.

<CodeSource path="examples/month-4/ros2-graph/m4_graph/config/aggregator.yaml" />

```yaml
# Parameters loaded by graph.launch.py. The top-level key is the node name.
aggregator_node:
  ros__parameters:
    window: 10          # readings per /summary message
filter_node:
  ros__parameters:
    alpha: 0.2          # starting smoothing factor (change it at runtime with /set_alpha)
```

The indentation is meaningful, as it always is in YAML. The top-level key is the node's name — `aggregator_node`, `filter_node` — and under it comes `ros__parameters`, with two underscores. That double underscore is not a typo; it is the fixed ROS 2 key, and a single underscore is not recognised. Underneath sit the parameter names and values. One file can hold the settings for several nodes, which is why both nodes appear here, and that is what makes it the natural companion to a launch file: one place for everything the graph needs.

The configuration node has two roles: it is a service server and a service client at the same time.

<CodeSource path="examples/month-4/ros2-graph/m4_graph/m4_graph/config_node.py" />

```python
"""Configuration node: a /set_alpha service that checks a new smoothing factor and then
sets the filter node's "alpha" parameter through that node's own parameter service."""
import rclpy
from rclpy.callback_groups import MutuallyExclusiveCallbackGroup
from rclpy.executors import ExternalShutdownException, MultiThreadedExecutor
from rclpy.node import Node
from rcl_interfaces.msg import Parameter, ParameterType
from rcl_interfaces.srv import SetParameters

from m4_interfaces.srv import SetAlpha


class ConfigNode(Node):
    def __init__(self):
        super().__init__('config_node')
        self.target = self.declare_parameter('target_node', 'filter_node').value
        # Every node offers <name>/set_parameters; this client calls the filter's one.
        # It gets its own callback group so its reply can arrive while on_set_alpha waits.
        self.client = self.create_client(SetParameters, f'/{self.target}/set_parameters',
                                         callback_group=MutuallyExclusiveCallbackGroup())
        self.create_service(SetAlpha, 'set_alpha', self.on_set_alpha)
        self.get_logger().info(f'/set_alpha ready (configures /{self.target})')

    def on_set_alpha(self, request, response):
        if not 0.0 < request.alpha <= 1.0:
            response.accepted = False
            response.message = f'rejected: alpha {request.alpha} is outside (0, 1]'
            return response
        param = Parameter(name='alpha')
        param.value.type = ParameterType.PARAMETER_DOUBLE
        param.value.double_value = request.alpha
        if not self.client.wait_for_service(timeout_sec=2.0):
            response.accepted = False
            response.message = f'/{self.target} is not running'
            return response
        result = self.client.call(SetParameters.Request(parameters=[param]))   # blocks this callback only
        ok = result.results[0].successful
        response.accepted = ok
        response.message = (f'alpha set to {request.alpha} on /{self.target}' if ok
                            else 'rejected by filter: ' + result.results[0].reason)
        self.get_logger().info(response.message)
        return response


def main():
    rclpy.init()
    node = ConfigNode()
    try:
        rclpy.spin(node, executor=MultiThreadedExecutor())   # two threads: service + client reply
    except (KeyboardInterrupt, ExternalShutdownException):
        pass
    finally:
        node.destroy_node()
        rclpy.try_shutdown()
```

Follow the two halves. The server half is `create_service(SetAlpha, 'set_alpha', self.on_set_alpha)`: whenever someone calls `/set_alpha`, `on_set_alpha` receives the request and fills the response. The client half is `create_client(SetParameters, ...)`, which talks to the filter node's parameter service. So the node validates the requested `alpha`, then forwards it, and reports what the filter said. That two-step is why the config node exists at all: it gives you one place that checks settings and could log or persist them, instead of every tool poking parameters directly and each tool needing its own copy of the rules.

Now the trap, because it is the single most common way to hang a ROS 2 node. Calling a service from inside a service callback deadlocks with the default single-threaded executor. Here is why: `on_set_alpha` runs on the executor's one and only thread, and `self.client.call(...)` blocks that thread while it waits for the reply. But the reply has to be received and processed by that same executor — which is busy waiting. Nobody is left to answer, so it waits forever. The fix used here has two parts: `MultiThreadedExecutor` gives the executor more than one thread, and the client's own `MutuallyExclusiveCallbackGroup` reserves a callback slot so its reply can be handled on another thread while `on_set_alpha` is still waiting. Asynchronous calls are the other way out, but this is the pattern to remember first.

## Actions

The aggregator node is the busiest one: it publishes a statistics message every `window` readings, and it offers the `/collect` action.

<CodeSource path="examples/month-4/ros2-graph/m4_graph/m4_graph/aggregator_node.py" />

```python
"""Aggregator: a /summary topic every `window` readings, and a /collect action that
gathers a requested number of readings, with feedback and cancellation."""
import threading

import rclpy
from rclpy.action import ActionServer, CancelResponse
from rclpy.callback_groups import ReentrantCallbackGroup
from rclpy.executors import ExternalShutdownException, MultiThreadedExecutor
from rclpy.node import Node

from m4_interfaces.action import Collect
from m4_interfaces.msg import Reading, Summary


class AggregatorNode(Node):
    def __init__(self):
        super().__init__('aggregator_node')
        self.window = self.declare_parameter('window', 10).value
        self.values = []
        self.collectors = []            # one list per running /collect goal
        self.new_reading = threading.Condition()
        group = ReentrantCallbackGroup()  # let the action run while readings arrive
        self.pub = self.create_publisher(Summary, 'summary', 10)
        self.create_subscription(Reading, 'input', self.on_reading, 10, callback_group=group)
        ActionServer(self, Collect, 'collect', self.execute, callback_group=group,
                     cancel_callback=self.on_cancel)
        self.get_logger().info(f'window {self.window}, listening on {self.resolve_topic_name("input")}')

    def on_reading(self, msg):
        self.values.append(msg.value)
        if len(self.values) == self.window:
            v = self.values
            self.pub.publish(Summary(count=len(v), mean=sum(v) / len(v),
                                     minimum=min(v), maximum=max(v)))
            self.values = []
        with self.new_reading:
            for c in self.collectors:
                c.append(msg.value)
            self.new_reading.notify_all()

    def on_cancel(self, goal_handle):
        with self.new_reading:
            self.new_reading.notify_all()   # wake execute() so it sees the request at once
        return CancelResponse.ACCEPT

    def execute(self, goal_handle):
        want = goal_handle.request.samples
        got = []
        with self.new_reading:
            self.collectors.append(got)
        try:
            sent = 0
            while sent < want:
                with self.new_reading:
                    self.new_reading.wait_for(
                        lambda: len(got) > sent or goal_handle.is_cancel_requested, timeout=0.5)
                if goal_handle.is_cancel_requested:
                    goal_handle.canceled()
                    self.get_logger().info(f'collect canceled after {sent} readings')
                    return self.result(got[:sent])
                while sent < min(len(got), want):
                    sent += 1
                    goal_handle.publish_feedback(Collect.Feedback(received=sent, latest=got[sent - 1]))
            goal_handle.succeed()
            return self.result(got[:want])
        finally:
            with self.new_reading:
                self.collectors.remove(got)

    @staticmethod
    def result(values):
        mean = sum(values) / len(values) if values else 0.0
        return Collect.Result(received=len(values), mean=mean)


def main():
    rclpy.init()
    node = AggregatorNode()
    try:
        rclpy.spin(node, executor=MultiThreadedExecutor())
    except (KeyboardInterrupt, ExternalShutdownException):
        pass
    finally:
        node.destroy_node()
        rclpy.try_shutdown()
```

The first thing to notice is the topic name: the subscription listens on `'input'`, a relative name, which the launch file remaps to `/filtered` in section 6. The node never hard-codes where its data comes from — it says "input" and lets the outside world decide what that connects to. That one decision is what makes the node reusable: record a bag, replay it, and the same node summarises a live sensor or a five-minute-old recording without a code change.

The `/collect` action is the new idea. `ActionServer(self, Collect, 'collect', self.execute, ...)` wires up a server whose job is `execute`, which runs once per goal. Read `execute` as a small state machine. It reads how many samples the goal wants, registers a fresh list to collect them into, then loops: it waits for a new reading to arrive (or for a cancel request), reports one feedback message per reading it has received, and finishes with either `succeed()` or `canceled()` plus a result. The `ReentrantCallbackGroup` and the `MultiThreadedExecutor` are there for the same reason as in section 4 — readings must keep arriving and being processed while `execute` is sitting in its wait, and a single thread would stall the whole node. `on_cancel` wakes `execute` up immediately so a cancellation takes effect at once rather than at the end of the next timeout.

Here is the summary topic in action, one message:

```text
count: 10
mean: 21.161432463771973
minimum: 20.974611788770712
maximum: 21.298657354248668
---
```

Ten readings averaged to about 21.16, with the smallest just under 21 and the largest just above it. Your exact numbers will differ because you are catching a different window of the sequence.

The action needs a client, and this one is also a useful tool.

<CodeSource path="examples/month-4/ros2-graph/m4_graph/m4_graph/collect_client.py" />

```python
"""Action client for /collect: send a goal, print the feedback, optionally cancel.

usage: ros2 run m4_graph collect_client <samples> [--cancel-after N]"""
import argparse

import rclpy
from rclpy.action import ActionClient
from rclpy.node import Node

from m4_interfaces.action import Collect


def main():
    parser = argparse.ArgumentParser()
    parser.add_argument('samples', type=int)
    parser.add_argument('--cancel-after', type=int, default=0, help='cancel after N feedback messages')
    args = parser.parse_args()

    rclpy.init()
    node = Node('collect_client')
    client = ActionClient(node, Collect, 'collect')
    client.wait_for_server()
    state = {'feedback': 0, 'handle': None}

    def on_feedback(msg):
        fb = msg.feedback
        print(f'feedback: {fb.received}/{args.samples}, latest {fb.latest:.2f}')
        state['feedback'] += 1
        if args.cancel_after and state['feedback'] == args.cancel_after and state['handle']:
            print('requesting cancel')
            state['handle'].cancel_goal_async()

    goal = client.send_goal_async(Collect.Goal(samples=args.samples), feedback_callback=on_feedback)
    rclpy.spin_until_future_complete(node, goal)
    state['handle'] = goal.result()
    if not state['handle'].accepted:
        print('goal rejected')
        return
    result = state['handle'].get_result_async()
    rclpy.spin_until_future_complete(node, result)
    status = {4: 'succeeded', 5: 'canceled', 6: 'aborted'}.get(result.result().status, 'unknown')
    r = result.result().result
    print(f'{status}: {r.received} readings, mean {r.mean:.2f}')
    node.destroy_node()
    rclpy.try_shutdown()
```

A goal is sent with `send_goal_async` and a `feedback_callback`, and the feedback function prints one line per reading as it arrives. A successful run of five samples looks like this:

```text
feedback: 1/5, latest 20.91
feedback: 2/5, latest 21.13
feedback: 3/5, latest 21.25
feedback: 4/5, latest 21.37
feedback: 5/5, latest 21.50
succeeded: 5 readings, mean 21.23
```

The feedback arrives as each reading does, which is the whole point of an action over a service: the client is not blind while it waits. Now ask for twenty samples but cancel after the third feedback:

```text
feedback: 1/20, latest 21.41
feedback: 2/20, latest 21.33
feedback: 3/20, latest 21.31
requesting cancel
canceled: 3 readings, mean 21.35
```

The cancelled goal still returns a result with what it had — three readings, and their mean. That is the property that makes actions the right tool for robot motion: you can stop the robot and still learn where it got to, so "cancel and report" is a normal outcome rather than an error. Lesson 5 writes an action that drives the robot a set distance; it has exactly this structure, with odometry in place of readings. You can drive the same thing by hand with `ros2 action send_goal --feedback` from a terminal, which is a handy way to poke an action without writing any code.

## Launch it all

Running four nodes means typing four commands into four terminals, which does not scale and is easy to get wrong — start them in the wrong order, forget to source, forget a parameter. A launch file solves all of that at once: it starts the whole graph with its parameters and its remappings from one command.

<CodeSource path="examples/month-4/ros2-graph/m4_graph/launch/graph.launch.py" />

```python
"""Start the whole Lesson 2 graph: sensor -> filter (C++) -> aggregator, plus the config node.

ros2 launch m4_graph graph.launch.py rate:=10.0 summary_topic:=stats"""
import os

from ament_index_python.packages import get_package_share_directory
from launch import LaunchDescription
from launch.actions import DeclareLaunchArgument
from launch.substitutions import LaunchConfiguration
from launch_ros.actions import Node


def generate_launch_description():
    params = os.path.join(get_package_share_directory('m4_graph'), 'config', 'aggregator.yaml')
    rate = LaunchConfiguration('rate')
    summary_topic = LaunchConfiguration('summary_topic')
    return LaunchDescription([
        DeclareLaunchArgument('rate', default_value='5.0', description='sensor rate in Hz'),
        DeclareLaunchArgument('summary_topic', default_value='summary',
                              description='where the aggregator publishes'),
        Node(package='m4_graph', executable='sensor_node',
             parameters=[{'rate': rate}]),
        Node(package='m4_graph_cpp', executable='filter_node',
             parameters=[params]),
        Node(package='m4_graph', executable='aggregator_node',
             parameters=[params],
             remappings=[('input', 'filtered'), ('summary', summary_topic)]),
        Node(package='m4_graph', executable='config_node'),
    ])
```

`DeclareLaunchArgument` and `LaunchConfiguration` are the pair that turns something into a command-line argument: the first declares it and gives a default, the second refers to its value when you build a node. `parameters=[...]` accepts either a dictionary of values like `{'rate': rate}` or a path to a YAML file like `params`. `remappings=[('input', 'filtered'), ...]` renames topics from outside the node, which is how the aggregator's `input` becomes `/filtered` and its `summary` becomes whatever `summary_topic` is. And `get_package_share_directory` finds the installed YAML file, so the launch file does not care where your workspace lives.

For `ros2 launch` to find the launch file and the YAML at runtime, both have to be installed by `setup.py`. Add these two lines to its `data_files` list:

```python
        ('share/' + package_name + '/launch', glob('launch/*.launch.py')),
        ('share/' + package_name + '/config', glob('config/*.yaml')),
```

Each says "copy everything matching this pattern into the package's share directory when installing". Without them the files sit in your `src/` folder and the launch command cannot see them — another version of the same install-time lesson from earlier.

## Bags and QoS

### Record and replay

`ros2 bag` records topics to a file and plays them back with the original timing, and in Jazzy the default file format is MCAP. It sounds minor and it is not: a problem that happens once an hour in the lab can be recorded once and then replayed as often as you like, because the recording does not care that the bug is rare. This is the tool behind "how do you debug anything that only fails occasionally" — you stop trying to catch it live and start keeping the data.

### QoS mismatches

The course names a gap in the available material. DDS and QoS are covered badly by every resource the course author could find — the topic is either skipped or buried — yet when a topic publishes but nothing receives, the answer is almost always a QoS mismatch. You will end up reading the official Concepts page, and it is worth knowing that going in.

QoS, quality of service, is a set of policies that each publisher and subscriber carries. A connection only forms if the two sides are compatible, and when they are not, the publisher keeps publishing and the subscriber silently stays empty. Three policies explain almost everything you will meet.

| Policy | Options | Rule |
| --- | --- | --- |
| Reliability | reliable (default) / best effort | a best-effort publisher cannot serve a reliable subscriber |
| Durability | volatile (default) / transient local | a transient-local subscriber gets the last messages a transient-local publisher kept (used for maps and robot descriptions); a volatile publisher with a transient-local subscriber is incompatible |
| History + depth | keep last N (default 10) / keep all | how many messages wait in the queue |

The reliability row is the one you will hit first. Sensor drivers often publish best effort, on purpose: the `sensor_data` profile is built around the idea that a lost lidar scan is better than a late one, so it does not re-send. A subscriber that asks for reliable delivery cannot be served by a best-effort publisher, and ROS 2 tells you so if you look. Here is the demonstration: a best-effort publisher, a reliable subscriber, then a best-effort one.

```text
$ ros2 topic echo --qos-reliability reliable /qos_demo std_msgs/msg/String
[WARN] [1792444212.682225980] [_ros2cli_440298]: New publisher discovered on topic '/qos_demo', offering incompatible QoS. No messages will be received from it. Last incompatible policy: RELIABILITY
$ ros2 topic echo --qos-reliability best_effort /qos_demo std_msgs/msg/String
data: hi
---
```

The first subscriber receives nothing and the log states the reason explicitly: the publisher offers an incompatible QoS, and the last incompatible policy was RELIABILITY. The second subscriber, matching best effort, receives the message immediately. When a topic "publishes but nothing receives", that warning is your best clue.

So here is the debug order, and it is short. First `ros2 topic info -v <topic>`, which lists each endpoint and its QoS — compare the publisher and subscriber configurations. Second, if the QoS looks fine, check `ROS_DOMAIN_ID` from Lesson 1: two terminals on different domains never see each other at all. Third, check the topic name and namespace, because a small typo or a missing remap produces the same silence. Work down that list before you touch your code.

## Composition: nodes are not processes

A launch file can start N node executables in N processes; remapping changes names, **not process placement**. A composable C++ node is a registered component in a shared library. `component_container` hosts a component manager that can load several components in one process while retaining distinct ROS node names. Our existing Python graph is not silently converted into C++ components by changing its launch file. The [Jazzy Composition tutorial](https://docs.ros.org/en/jazzy/Tutorials/Intermediate/Composition.html) supplies the separate `composition` demo package used below. The [Jazzy About-Composition page](https://docs.ros.org/en/jazzy/Concepts/Intermediate/About-Composition.html) lists three generic containers: `component_container` runs all components on one SingleThreadedExecutor, `component_container_mt` runs them on one MultiThreadedExecutor, and `component_container_isolated` gives each component its own dedicated executor (SingleThreadedExecutor by default, MultiThreadedExecutor with `--use_multi_threaded_executor`).

**Real `component_container`, ROS graph and robot runs: 本页未运行.** Reading recipe: source Jazzy in each terminal as above and ensure `rclcpp_components`, `ros2component` and `composition` are installed. Terminal A runs the container and stays open; terminal B lists types, then loads the two components:

```bash
# Terminal A
ros2 run rclcpp_components component_container
# Terminal B
ros2 component types
ros2 component load /ComponentManager composition composition::Talker
ros2 component load /ComponentManager composition composition::Listener
ros2 component list
```

The two components share one OS process but remain `/talker` and `/listener` in the graph. Composition is not just remapping, a DOMAIN_ID change or a QoS acceptance test.

### Shared workload, explicit accounting and one injected crash

This **synthetic deterministic** sweep uses N=2/4/8 components, 12 ticks and the same publisher stream in both deployments. Component i has one scheduled callback when `(tick+i)%3==0`, processing payload `(tick+1)*(i+1)`. Every healthy process polls once per tick, including idle ticks; a container polls once and dispatches all its components. This is a declared **counter model**, not a claim that ROS or Linux always follows this scheduler. `processes` counts initially deployed processes, not survivors after a crash. `poll_ticks` is the sum of these per-process polls, `callbacks` counts completed jobs, and `checksum` sums processed payloads. The shared inputs and equal callback work are the comparison budget; there is no random sampling and therefore no seed-derived spread.

Healthy N=4 gives 4 versus 1 processes and 48 versus 12 poll ticks, but both complete 16 callbacks with checksum 248. The equality checks workload preservation, not measured speed. Then both deployments inject the **same component-1 fatal process crash just before tick 5**, with no restart. Separate deployment loses that process (direct crash blast radius 1); the shared container loses all N components (radius N). `lost_callbacks` counts scheduled jobs after their containing process dies; no downstream cascade, IPC loss, blocking callback, resource saturation or recovery is simulated. At N=4 the separate arm loses 3 callbacks versus 9 for the container. Lower polling counts and smaller crash domains pull in different directions: no universal winner is presumed.

"""Synthetic deterministic pub/sub scheduling counters, NOT ROS benchmarks.
Every component gets the same immutable command stream in both deployments.
Each process polls once per tick, even idle: a declared accounting assumption,
not Linux context switches or CPU time. Callbacks use the same work function.
Fault injection kills the process containing component 1 before tick 5;
no restart, shared dependencies or downstream cascade are modelled.
"""
from dataclasses import dataclass

TICKS = 12
CRASH_TICK = 5


@dataclass(frozen=True)
class Result:
    processes: int
    polls: int
    callbacks: int
    checksum: int
    lost_callbacks: int
    blast_radius: int


def run(n, composed, fault=False):
    if n < 2:
        raise ValueError("need at least two components")
    groups = (tuple(range(n)),) if composed else tuple((i,) for i in range(n))
    polls = callbacks = checksum = lost = 0
    victims = next(group for group in groups if 1 in group) if fault and CRASH_TICK < TICKS else ()
    for tick in range(TICKS):
        for group in groups:
            dead = fault and tick >= CRASH_TICK and 1 in group
            if not dead:
                polls += 1
            for component in group:
                # One publisher fan-out stream, same subscription schedule and payloads.
                if (tick + component) % 3 == 0:
                    if dead:
                        lost += 1
                    else:
                        callbacks += 1
                        checksum += (tick + 1) * (component + 1)
    return Result(len(groups), polls, callbacks, checksum, lost, len(victims))


def main():
    print("Synthetic shared stream: ticks=12; equal callback work; deterministic N sweep (no seeds).")

## QoS Deadline and Lifespan: time guarantees on a topic

The QoS section above is about whether a publisher and a subscriber connect at all: a reliability or durability mismatch leaves the subscriber silently empty. Two other policies say nothing about whether a sample arrives, only **when**. **Deadline** is the longest the subscription expects to wait between messages, and **Lifespan** is how old a message may be on arrival before it is thrown away. This section puts both on one shared timeline and compares them with a reliability-only subscription. It is **not** the reliability mismatch above (every pair here is compatible and connected), **not** the bag QoS replay, **not** composition, and **not** a FreeRTOS task deadline from Month 2.

<Resource id="ros2-qos" />

**Source actually opened (HTML body read): ROS 2 Jazzy, "Quality of Service settings".**

- **Deadline:** "the expected maximum amount of time between subsequent messages being published to a topic".
- **Lifespan:** "the maximum amount of time between the publishing and the reception of a message without the message being considered stale or expired"; expired messages "are silently dropped and are effectively never received".
- **Liveliness and lease duration:** a publisher must show it is alive within the lease duration, either automatically when any of the node's publishers publishes or manually by topic. The toy does not model liveliness.
- Defaults: deadline, lifespan and lease durations are all "default", which the middleware usually reads as infinitely long.
- **Compatibility** (request vs offered): offered deadline x and requested y connect only if y is not shorter than x; a default offer with a set request does not connect. The same rule holds for lease duration.
- **QoS events:** "offered deadline missed" (the publisher has not published within the deadline) and "requested deadline missed" (the subscription has not received a message within it), alongside liveliness lost / changed and incompatible QoS.
- Statements 以原文为准. A real `ros2 topic` run or rclpy QoS event callbacks: **本页未运行**.

### Deadline, lifespan and the age of the sample you act on

<Formula label="Lifespan: a sample is dropped on arrival when">t_recv − t_stamp > lifespan</Formula>

<Formula label="Requested deadline misses in a gap g between received samples (toy count)">misses = ⌈g / deadline⌉ − 1</Formula>

<Formula label="Oldest sample a deadline + lifespan subscriber can act on">age ≤ lifespan + deadline</Formula>

**Worked example.** The toy publishes every 10 ms. Arm B sets lifespan 10 ms and deadline 20 ms. A sample is accepted only if it arrives within 10 ms of its stamp, and the controller acts only while the last accepted sample came in no more than 20 ms ago, so the oldest sample B can act on is `10 + 20 = 30 ms` old; a reliability-only subscriber has no bound at all. With a 50 ms gap between accepted samples, B counts `⌈50 / 20⌉ − 1 = 2` deadline misses (at 20 and 40 ms into the gap); a gap of exactly 20 ms is not a miss. Arm C sets a 5 ms deadline against a 10 ms period, so every gap of 9 to 11 ms counts one or two misses by construction: about 2000 gaps in 20 s give about 3000 misses.

**Correctness criterion for the counts.** A miss is counted only when a gap between accepted receptions is longer than the deadline, and a lifespan drop only when `t_recv − t_stamp` is larger than the lifespan; a retransmitted sample is neither, it is only late. A test builds a five-sample timeline by hand and checks the drops, misses, holds and stale uses.

**No integration step here.** The toy has no plant and no time stepping: it compares integer-microsecond event times, so every comparison is exact and there is no step-size criterion. A test checks that every time is an integer.

### Fair setup

`qos_deadline_lifespan_toy.py` is **synthetic** and stdlib only, a discrete-event stand-in for one publisher and one subscription, **not** an rmw or DDS implementation. **Model assumptions:**
- The publisher stamps a sample every 10 ms ± 1 ms; in `late_sensor` it sometimes stalls. Each sample arrives 1–3 ms later; in `lossy_reliable` a lost first transmission is repaired 10–30 ms later. Reliable delivery is modelled only as that extra delay.
- The subscriber keeps the newest stamp it has received; an older sample arriving later is ignored by every arm.
- A controller tick runs every 10 ms with a per-seed phase. At each tick an arm acts on its current sample or holds. A sample older than 25 ms at use counts as a **stale use**.

| Arm | Requested deadline | Lifespan | Behaviour |
|---|---|---|---|
| A_rel | default (infinite) | default (infinite) | acts on the newest sample whatever its age |
| B_dl | 20 ms | 10 ms | drops samples older than 10 ms on arrival; holds while the deadline is missed |
| C_tight | 5 ms (offered 5 ms too) | 10 ms | as B, with a deadline shorter than the publish period |

**Common random numbers:** for each (regime, seed), publication times, stalls, delays, losses and the controller phase are drawn once and shared by all three arms; 20 s per seed, five seeds. Metrics: stale-use % of ticks, hold % of ticks, mean age of the samples acted on (ms), requested-deadline misses and lifespan drops.

| Regime | Stalls | Loss and repair | Expected (written before the first run) |
|---|---|---|---|
| late_sensor | prob 0.01, 40–120 ms | none | B consistent fewer stale uses than A; B pays hold ticks |

| lossy_reliable | none | 0.15, repaired after 10–30 ms | B ties A on stale uses and loses on hold % |

**Choices made after seeing results.** No parameter was changed. The three regimes, the period, the 25 ms stale bound and the QoS values were written down before the first run. One expectation did **not** hold (see `lossy_reliable`) and is printed as it came out. """ROS 2 QoS Deadline and Lifespan vs a reliability-only subscription, on one shared timeline.

Synthetic, stdlib only.  A discrete-event stand-in for one publisher and one subscription; it is
not an rmw / DDS implementation and makes no claim about bit-exact middleware behaviour.  Not the
reliability / durability *mismatch* earlier on this page (there every pair here is compatible and
connected), not the bag QoS replay, not composition, and not a FreeRTOS task deadline (Month 2).
Real `ros2 topic` / rclpy QoS events: 本页未运行.  ROS 2 Jazzy "Quality of Service settings"
definitions are 以原文为准:
  Deadline: the expected maximum amount of time between subsequent messages being published.
  Lifespan: the maximum time between publishing and reception before a message is stale or
            expired; expired messages are silently dropped.
  Requested deadline missed: the subscription has not received a message within the deadline.
  Offered deadline missed: the publisher has not published within the deadline.
  Compatibility: a subscription requesting a deadline shorter than the one offered is not
            connected (offered x, requested y < x: No).
Timeline (integer microseconds, so every comparison is exact): the publisher stamps a sample
every PERIOD with jitter; in late_sensor it sometimes stalls.  Each sample reaches the subscriber
after a network delay; a lost first transmission is repaired by a retransmission (reliable
delivery), modelled only as extra delay.  The subscriber keeps the newest stamp it has received
(an older sample arriving later is ignored by every arm).  A controller tick runs every PERIOD
with a per-seed phase; at each tick an arm either acts on its current sample or holds.
No integration step: there is no plant and no time stepping, only event times in microseconds,
so there is no step-size criterion (a test checks that all times are integers).
Common random numbers: for each (regime, seed) the publication times, stalls, delays, losses and
the controller phase are drawn once and shared by all three arms; five seeds.
Arms (same publication, delay, loss and tick draws):
  A_rel     reliability only (deadline and lifespan left at default, i.e. infinite): acts on the
            newest received sample whatever its age.
  B_dl      requested deadline DL_B and lifespan LS_B: a sample older than LS_B on arrival is
            dropped; if no sample has been accepted for longer than DL_B (requested deadline
            missed) the controller holds instead of acting.
  C_tight   the same with deadline DL_C shorter than the publish period, offered and requested
            alike (compatible), so the deadline is missed on almost every gap by construction.
Metrics per seed: stale-use % (ticks that act on a sample older than STALE), hold % (ticks with
no action), mean age of the samples acted on (ms), requested-deadline-missed events, lifespan
drops.  A deadline miss is counted per gap g between accepted receptions as ceil(g / DL) - 1, so
a gap exactly equal to the deadline is not a miss.
Regimes and expectations, written before the first run:
  late_sensor     stalls (prob 0.01, 40-120 ms), delay 1-3 ms, no loss
                  B consistent fewer stale uses than A (B pays hold ticks)
  on_time         no stalls, delay 1-3 ms, no loss       A and B tie (no misses, no drops)
  lossy_reliable  no stalls, loss 0.15 repaired after 10-30 ms
                  B ties A on stale uses and loses on hold % (lifespan drops the repaired samples)
  C_tight holds on most ticks in every regime (consistent loss to B on hold %).
"""
import math
import random

SEEDS = (0, 1, 2, 3, 4)
MS = 1000                # microseconds per millisecond
PERIOD = 10 * MS         # publish and control period
JITTER = 1 * MS          # publish jitter, uniform +-
DURATION = 20000 * MS    # 20 s
STALE = 25 * MS          # a sample older than this at use is stale for the controller
DL_B, LS_B = 20 * MS, 10 * MS
DL_C, LS_C = 5 * MS, 10 * MS
NUM_ZERO = 1e-9
ARMS = ("A_rel", "B_dl", "C_tight")
# name: (stall prob, stall min ms, stall max ms, loss prob, repair min ms, repair max ms); before the first run
REGIMES = {
    "late_sensor": (0.01, 40, 120, 0.0, 0, 0),
    "on_time": (0.0, 0, 0, 0.0, 0, 0),
    "lossy_reliable": (0.0, 0, 0, 0.15, 10, 30),
}
STREAM = {"late_sensor": 0, "on_time": 1, "lossy_reliable": 2}
QOS = {"A_rel": (None, None), "B_dl": (DL_B, LS_B), "C_tight": (DL_C, LS_C)}


def compatible(offered, requested):
    """Deadline compatibility table of the Jazzy page; None stands for 'default' (infinite)."""
    if requested is None:
        return True
    if offered is None:
        return False
    return requested >= offered


def shared_draws(regime, seed):
    rng = random.Random(1000 * STREAM[regime] + seed)
    p_stall, s_min, s_max, p_loss, r_min, r_max = REGIMES[regime]
    samples, t = [], 0
    while True:
        t += PERIOD + rng.randint(-JITTER, JITTER)
        if p_stall and rng.random() < p_stall:
            t += rng.randint(s_min * MS, s_max * MS)
        if t > DURATION:
            break
        delay = rng.randint(1 * MS, 3 * MS)
        if p_loss and rng.random() < p_loss:
            delay += rng.randint(r_min * MS, r_max * MS)
        samples.append((t, t + delay))
    phase = rng.randint(0, PERIOD - 1)
    ticks = list(range(PERIOD + phase, DURATION + 1, PERIOD))
    return samples, ticks


def run_arm(arm, draw):
    samples, ticks = draw
    deadline, lifespan = QOS[arm]
    arrivals = sorted(samples, key=lambda s: (s[1], s[0]))
    accepted, drops = [], 0
    newest = -1
    for stamp, recv in arrivals:
        if lifespan is not None and recv - stamp > lifespan:
            drops += 1
            continue
        if stamp > newest:
            newest = stamp
            accepted.append((recv, stamp))
    misses = 0
    if deadline is not None:
        for (r0, _), (r1, _) in zip(accepted, accepted[1:]):
            gap = r1 - r0
            misses += max(0, -(-gap // deadline) - 1)
    stale = hold = 0
    ages = []
    k, cur, last_recv = 0, None, None
    for t in ticks:
        while k < len(accepted) and accepted[k][0] <= t:
            last_recv, cur = accepted[k]
            k += 1
        if cur is None or (deadline is not None and t - last_recv > deadline):
            hold += 1
            continue
        age = t - cur
        ages.append(age)
        if age > STALE:
            stale += 1
    n = len(ticks)
    return {"stale": 100.0 * stale / n, "hold": 100.0 * hold / n,
            "age": (sum(ages) / len(ages) / MS) if ages else 0.0, "miss": float(misses), "drop": float(drops)}


def mean_sd(xs):
    mu = sum(xs) / len(xs)
    return mu, math.sqrt(sum((x - mu) ** 2 for x in xs) / (len(xs) - 1))


def num(x):
    if x != 0.0 and abs(x) < 5e-5:
        return f"{x:.3e}"
    return f"{x:.4f}"


def sign_note(diffs, m):
    n, opp, zero = len(diffs), sum(1 for d in diffs if d * m < 0), sum(1 for d in diffs if d == 0)
    if opp == 0 and zero == 0:
        return f"same sign on all {n} seeds"
    if opp == 0:
        return f"no seed has the opposite sign, {zero} of {n} equal"
    note = f"{opp} of {n} seeds {'has' if opp == 1 else 'have'} the opposite sign"
    return note + (f", {zero} of {n} equal" if zero else "")


def verdict(xa, xb):
    diffs = [a - b for a, b in zip(xa, xb)]
    if all(d == 0.0 for d in diffs):
        return "0.0000+-0.0000: tie: identical on every seed"
    m, s = mean_sd(diffs)
    if abs(m) < NUM_ZERO and s < NUM_ZERO:
        return f"{num(m)}+-{num(s)}: numerically zero (floating-point residue), effectively a tie"
    if abs(m) <= s:
        label = "near-tie / small gap, within seed noise (|m| <= sd)"
    elif abs(m) < 0.2 * min(abs(mean_sd(xa)[0]), abs(mean_sd(xb)[0])):
        label = "small but consistent gap, not a tie (|m| > sd)"
    else:
        label = "clear gap, not a tie (|m| > sd)"
    return f"{num(m)}+-{num(s)}: {label}; {sign_note(diffs, m)}"


def main():
    print("Synthetic ROS 2 QoS stand-in: reliability only vs deadline + lifespan vs a deadline tighter than the period; not rmw / DDS")
    print(f"PERIOD={PERIOD // MS} ms JITTER=+-{JITTER // MS} ms DURATION={DURATION // MS // 1000} s STALE={STALE // MS} ms "
          f"B: deadline {DL_B // MS} ms lifespan {LS_B // MS} ms; C: deadline {DL_C // MS} ms lifespan {LS_C // MS} ms; seeds={len(SEEDS)}")
    print("no integration step: integer-microsecond event times, no plant")
    print(f"compatibility (Jazzy table): offered 20 ms / requested 20 ms -> {compatible(20, 20)}; offered 20 / requested 5 -> "
          f"{compatible(20, 5)} (no connection); offered 5 / requested 20 -> {compatible(5, 20)}; offered default / requested 20 -> {compatible(None, 20)}")
    print("regime arm stale_use_% hold_% mean_age_ms deadline_misses lifespan_drops  (mean+-sd over seeds)")
    for regime, (p_stall, s_min, s_max, p_loss, r_min, r_max) in REGIMES.items():
        print(f"{regime} (stall prob {p_stall}, {s_min}-{s_max} ms; loss {p_loss}, repaired after {r_min}-{r_max} ms)")
        draws = [shared_draws(regime, s) for s in SEEDS]
        res = {arm: [run_arm(arm, d) for d in draws] for arm in ARMS}
        for arm in ARMS:
            cols = ["{}+-{}".format(*map(num, mean_sd([r[k] for r in res[arm]]))) for k in ("stale", "hold", "age", "miss", "drop")]
            print(f"  {arm} " + " ".join(cols))
        for x, y in (("B_dl", "A_rel"), ("C_tight", "B_dl")):
            for key in ("stale", "hold", "age"):
                print(f"  paired {x[0]}-{y[0]} {key}: {verdict([r[key] for r in res[x]], [r[key] for r in res[y]])}")
    print("No winner declared: deadline + lifespan trade stale actions for hold ticks; they cost nothing on an on-time stream and cost holds when late repairs are dropped")
    print("Real ros2 topic / rclpy QoS events: 本页未运行; ROS 2 Jazzy QoS definitions 以原文为准")


if __name__ == "__main__":
    main()

### Read the regimes

How the labels are used on this page, in this order: **tie: identical on every seed** only when the paired per-seed difference is exactly zero on every seed; **numerically zero (floating-point residue), effectively a tie** when `|paired mean|` and its sd are both below 1e-9 (no sign count is printed on such a line); **near-tie / small gap, within seed noise** when `|paired mean| ≤ sd`; otherwise a **consistent** gap (`|paired mean| > sd`), called **small** if `|m|` is under 20 % of the smaller arm mean and **clear** otherwise; the 20 % rule only chooses between those two words. Every consistent line carries a same-sign count over the 5 seeds, and any seed with the opposite sign is reported; a sign count alone never makes a gap consistent. Gaps are computed from unrounded values. Paired differences are B−A and C−B. `stale` is stale-use % of ticks, `hold` hold % of ticks, `age` the mean age of the samples acted on in ms.

- **late_sensor:**
  - **Deadline + lifespan win with a clear gap on stale uses:** B−A stale −6.6633±1.6806 points, same sign on all 5 seeds. During a stall A keeps acting on the last sample, which can grow past 100 ms old; B stops acting once the deadline is missed.
  - The price is the same size: B−A hold 6.9535±1.8594 points, clear, 5/5. B does not make the data fresher; it turns stale actions into holds, and what a hold does (stop, coast, brake) is the controller's choice.
- **on_time:**
  - With no stalls and no loss, every gap is shorter than 20 ms and every delay shorter than 10 ms, so B never drops a sample or misses a deadline, and both arms hold only before the first sample arrives: B−A stale, hold and age are each a **tie: identical on every seed**.
- **lossy_reliable:**
  - The expected tie on stale uses did **not** happen: B−A stale −1.0705±0.1824 points, clear, 5/5. When two samples in a row need repair, A acts on a sample more than 25 ms old; B has already dropped them.
  - **B loses on hold with a clear gap:** B−A hold 2.7814±0.3652 points, same sign on all 5 seeds. Lifespan drops every repaired sample (about 300 per seed) even though most of them would not have been stale at use.
- **C_tight:** in every regime, C holds on about half of the ticks (C−B hold 44.2821 to 52.9765 points, clear, 5/5) and counts about 3000 deadline misses in 20 s. A deadline shorter than the publish period does not make anything faster; it only reports misses that are certain.

The page **does not declare a universal winner**: deadline and lifespan cost nothing on a stream that is on time, turn stale actions into holds when the sensor stalls, and turn late repairs into holds when the network is lossy.

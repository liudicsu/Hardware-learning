A robot that knows where it is and has a map of where it is going can do something genuinely useful: you click a point on the floor plan and it drives there by itself, around the furniture, without you steering. That needs two things at once. To build a map, the robot has to know where it was when it saw each wall. To know where it is, it has to compare what it sees with a map. **SLAM** (simultaneous localization and mapping) solves both together, and **Nav2** turns "where I am" plus "where I want to be" into wheel commands.

This is the sixth and last lesson of Month 4. Everything it needs is already in place: m4bot from Lesson 3, the obstacles world and the lidar from Lesson 4, and `diff_drive_controller` from Lesson 5, which publishes odometry and accepts `TwistStamped` commands. Today we add three packages that every ROS 2 mobile robot uses — SLAM Toolbox for the map, Nav2 for the driving and `nav2_map_server` for saving the map — and one habit that saves hours: checking odometry before trusting any map built on it.

The practice task follows the order you would use on a real robot: calibrate odometry against the lidar, map the room and save the map, navigate in the saved map, then break navigation on purpose and find out why. The month's milestone is **map a room with SLAM Toolbox and navigate it autonomously with Nav2**.

## SLAM in one picture

Odometry alone is not enough. `diff_drive_controller` integrates wheel rotations into a pose, and every small error — a wheel that slips, a radius that is half a millimetre off, a turn that comes out one degree long — is added up forever. After a few minutes of driving, odometry can be tens of centimetres and several degrees away from the truth, and it never notices. The lidar, on the other hand, sees the walls directly, but a single scan does not say where the robot is unless you already have a map to compare it with.

SLAM Toolbox combines the two. It keeps a **pose graph**: every time the robot has moved 0.2 m or turned 0.2 rad, it stores the current scan together with the pose where it was taken. Each new scan is matched against the recent ones (scan matching), which corrects the small odometry errors as they happen. When the robot comes back to a place it has seen before, SLAM Toolbox recognises the scan (a **loop closure**) and adjusts the whole graph so that the old and new views agree. The map is then drawn from all the scans at their corrected poses.

The result appears in TF as one extra frame. The chain from the map to the robot is:

```text
map ──► odom ──► base_footprint ──► base_link ──► laser_link ...
    │         │                   │
    │         │                   └ robot_state_publisher (URDF, Lesson 3)
    │         └ diff_drive_controller (wheel odometry, Lesson 5): smooth, drifts slowly
    └ SLAM Toolbox: jumps a little whenever a scan match corrects the drift
```

SLAM Toolbox does not overwrite odometry. It publishes `map → odom`, the correction that makes the whole chain land in the right place. Odometry stays smooth for the controllers that need a continuous signal, and the map frame stays right for planning. When SLAM Toolbox corrects drift, only `map → odom` moves.

## Check odometry first

SLAM Toolbox uses odometry as its first guess for every scan match. If odometry is only a little off, scan matching fixes it. If it is badly off — say every turn comes out ten per cent too short — the first guess lands far from the truth, matching may lock onto the wrong wall, and the map comes out smeared or doubled. So before mapping, measure how good odometry is.

The cleanest test for a differential-drive robot is a full turn on the spot. Turning is where odometry is weakest, because the turn angle depends on the wheel separation, and the real separation is where the tyres touch the ground, not where the CAD drawing says. A full turn also has a built-in reference: after exactly 360°, the room looks exactly as it did before. `spin_check.py` turns the robot until odometry says 360°, then compares the lidar scan before and after. If the robot really turned 365°, every wall appears 5° further round, and the script finds the rotation that lines the two scans up.

<CodeSource path="examples/month-4/slam-nav/spin_check.py" />

```python
#!/usr/bin/env python3
"""Check odometry's heading against the lidar: spin m4bot one full turn by odometry, then ask the
lidar how far it really turned.

usage: python3 spin_check.py        (with control.launch.py or slam.launch.py running)
If odometry is right, the room looks the same to the lidar before and after one turn. If not, the
two scans are rotated against each other, and the rotation is the odometry's heading error."""
import math

import rclpy
from geometry_msgs.msg import TwistStamped
from nav_msgs.msg import Odometry
from rclpy.node import Node
from rclpy.parameter import Parameter
from rclpy.qos import qos_profile_sensor_data
from sensor_msgs.msg import LaserScan


class SpinCheck(Node):
    def __init__(self):
        super().__init__('spin_check', parameter_overrides=[Parameter('use_sim_time', value=True)])
        self.cmd = self.create_publisher(TwistStamped, 'diff_drive_controller/cmd_vel', 10)
        self.create_subscription(Odometry, 'diff_drive_controller/odom', self.on_odom, 1)
        self.scans = []
        self.create_subscription(LaserScan, 'scan', self.scans.append, qos_profile_sensor_data)
        self.yaw = None

    def on_odom(self, msg):
        q = msg.pose.pose.orientation
        self.yaw = math.atan2(2 * (q.w * q.z + q.x * q.y), 1 - 2 * (q.y * q.y + q.z * q.z))

    def send(self, w):
        msg = TwistStamped()
        msg.header.stamp = self.get_clock().now().to_msg()
        msg.twist.angular.z = w
        self.cmd.publish(msg)

    def average_scan(self, count=5):
        """Mean of the next `count` scans; beams without a hit count as the lidar's maximum range."""
        self.scans.clear()
        while len(self.scans) < count:
            rclpy.spin_once(self, timeout_sec=0.1)
        top = self.scans[0].range_max
        return [sum(min(s.ranges[i], top) for s in self.scans) / count
                for i in range(len(self.scans[0].ranges))]

    def settle(self, seconds):
        end = self.get_clock().now().nanoseconds + seconds * 1e9
        while self.get_clock().now().nanoseconds < end:
            self.send(0.0)
            rclpy.spin_once(self, timeout_sec=0.05)

    def run(self):
        while self.yaw is None:
            rclpy.spin_once(self, timeout_sec=0.1)
        before = self.average_scan()
        turned, last = 0.0, self.yaw
        while turned < 2 * math.pi - 0.002:              # one full turn, counted by odometry
            remaining = 2 * math.pi - turned
            self.send(max(0.05, min(0.5, 2.0 * remaining)))
            rclpy.spin_once(self, timeout_sec=0.05)
            step = math.atan2(math.sin(self.yaw - last), math.cos(self.yaw - last))
            turned, last = turned + step, self.yaw
        self.settle(1.0)
        after = self.average_scan()
        turned += math.atan2(math.sin(self.yaw - last), math.cos(self.yaw - last))
        error = best_shift(before, after)
        odom_deg, real_deg = math.degrees(turned), math.degrees(turned) + error
        print(f'odometry says: {odom_deg:.1f} deg')
        print(f'lidar says:    {real_deg:.1f} deg  (scans rotated by {error:+.1f} deg)')
        print(f'odometry / real = {odom_deg / real_deg:.3f}')


def best_shift(before, after, step=0.1, limit=60.0):
    """The angle (deg) that turns the `before` scan into the `after` one, to `step` degrees.

    A robot that turned d degrees too far sees every wall d degrees further clockwise, so
    after(theta) = before(theta + d). Beams are 1 degree apart; in between we interpolate."""
    n = len(before)

    def at(scan, deg):
        i = math.floor(deg) % n
        f = deg - math.floor(deg)
        return scan[i] * (1 - f) + scan[(i + 1) % n] * f

    def cost(d):
        return sum(abs(after[i] - at(before, i + d)) for i in range(n))

    shifts = [k * step - limit for k in range(int(2 * limit / step) + 1)]
    return min(shifts, key=cost)


def main():
    rclpy.init()
    node = SpinCheck()
    node.run()
    node.destroy_node()
    rclpy.shutdown()


if __name__ == '__main__':
    main()
```

The lidar has 360 beams, one per degree; `best_shift` interpolates between beams to estimate the rotation to 0.1°. Averaging five scans before and after removes most of the lidar's noise. Run it with Lesson 5's launch file, which loads the controller exactly as Lesson 5 left it:


That is a large error. Odometry thought it had turned 360°, but the robot really turned about 403°, 12 % more. Straight lines were fine in Lesson 5 (the drive-distance action stopped within 3 mm), so the wheel radius is right and the separation is wrong. In this simulation the wheel–ground contact makes the 0.28 m wheel base behave like a narrower one; on a real robot the cause is usually tyres that are wider or softer than the drawing. Either way the fix is the same, because `diff_drive_controller` has a parameter for it:

<Formula label="Separation calibration">new multiplier = old multiplier × odometry angle ÷ real angle</Formula>

Here that is 1.0 × 360 ÷ 403.1 = 0.893. The editor's first calibration run gave 0.896, which is what `odom_calibration.yaml` uses; the 0.003 difference is run-to-run variation of the contact model and well inside what you can measure this way.

### Drive the tour

Now drive the robot around until every wall and obstacle has been seen from more than one side. With a keyboard you would run `ros2 run teleop_twist_keyboard teleop_twist_keyboard --ros-args -p stamped:=true -p use_sim_time:=true -r cmd_vel:=/diff_drive_controller/cmd_vel`, as in Lesson 5. For a repeatable result the editor used a script that does the same thing: spin on the spot, then drive to two opposite corners and back.

<CodeSource path="examples/month-4/slam-nav/tour.py" />

```python
#!/usr/bin/env python3
"""Drive m4bot along a fixed tour of the obstacles room, so SLAM Toolbox sees every corner.

usage: python3 tour.py        (with slam.launch.py running)
The same thing you would do with teleop_twist_keyboard, but repeatable: it turns on the spot and
drives between waypoints, steering by odometry. It prints the odometry pose at each waypoint."""
import math

import rclpy
from geometry_msgs.msg import TwistStamped
from nav_msgs.msg import Odometry
from rclpy.node import Node
from rclpy.parameter import Parameter

# (x, y) in the odom frame, which starts where the robot was spawned: the room's centre
WAYPOINTS = [(1.4, 1.4), (-1.2, -1.2), (0.0, 0.0)]


class Tour(Node):
    def __init__(self):
        # stamp commands with the simulator's clock, like every node in a simulation
        super().__init__('tour', parameter_overrides=[Parameter('use_sim_time', value=True)])
        self.cmd = self.create_publisher(TwistStamped, 'diff_drive_controller/cmd_vel', 10)
        self.create_subscription(Odometry, 'diff_drive_controller/odom', self.on_odom, 1)
        self.pose = None

    def on_odom(self, msg):
        p, q = msg.pose.pose.position, msg.pose.pose.orientation
        yaw = math.atan2(2 * (q.w * q.z + q.x * q.y), 1 - 2 * (q.y * q.y + q.z * q.z))
        self.pose = (p.x, p.y, yaw)

    def send(self, v, w):
        msg = TwistStamped()
        msg.header.stamp = self.get_clock().now().to_msg()
        msg.twist.linear.x, msg.twist.angular.z = v, w
        self.cmd.publish(msg)

    def step(self):
        rclpy.spin_once(self, timeout_sec=0.05)

    def turn_to(self, target):
        while True:
            self.step()
            err = math.atan2(math.sin(target - self.pose[2]), math.cos(target - self.pose[2]))
            if abs(err) < 0.02:
                break
            self.send(0.0, max(-0.6, min(0.6, 2.0 * err)))   # slow turns keep the scans sharp
        self.send(0.0, 0.0)

    def drive_to(self, x, y):
        while True:
            self.step()
            dx, dy = x - self.pose[0], y - self.pose[1]
            if math.hypot(dx, dy) < 0.05:
                break
            err = math.atan2(dy, dx) - self.pose[2]
            err = math.atan2(math.sin(err), math.cos(err))
            self.send(min(0.25, math.hypot(dx, dy)), 2.0 * err)
        self.send(0.0, 0.0)

    def run(self):
        while self.pose is None:
            self.step()
        print('spin once on the spot')
        for target in (math.pi / 2, math.pi, -math.pi / 2, 0.0):
            self.turn_to(target)
        for x, y in WAYPOINTS:
            self.turn_to(math.atan2(y - self.pose[1], x - self.pose[0]))
            self.drive_to(x, y)
            print(f'at waypoint ({x:.1f}, {y:.1f}): odom x {self.pose[0]:.2f} y {self.pose[1]:.2f}')
        self.turn_to(0.0)
        print(f'done, facing +x again: yaw {math.degrees(self.pose[2]):.0f} deg')


def main():
    rclpy.init()
    node = Tour()
    node.run()
    node.destroy_node()
    rclpy.shutdown()


if __name__ == '__main__':
    main()
```

```python
"""Check a saved map against the world it came from: are the walls and obstacles where the
obstacles world (Lesson 4) put them?

usage: python3 map_check.py ~/maps/room.yaml      (exit code 1 if an object is missing or the map is too empty)
Reads the .yaml and .pgm written by nav2_map_server's map_saver_cli. Only the Python standard
library is needed. The map frame starts where the robot was spawned, the centre of the room."""
import os
import sys

# what is really in the obstacles world, in the map frame (centre x, centre y, half x, half y)
OBJECTS = {
    'north wall': (3.0, 0.0, 0.05, 3.0),
    'south wall': (-3.0, 0.0, 0.05, 3.0),
    'west wall': (0.0, 3.0, 3.05, 0.05),
    'east wall': (0.0, -3.0, 3.05, 0.05),
    'red box': (2.0, 0.0, 0.2, 0.2),
    'blue pillar': (1.0, -1.2, 0.15, 0.15),
    'green block': (-1.5, 1.5, 0.6, 0.6),   # 1.2 x 0.3 m turned 0.6 rad: check its bounding square
}
# The fewest occupied cells that still count as "found", and the fewest occupied and free cells
# in the whole map: about half the smaller count seen in two real runs of tools/sim/ros/run.sh
# (2026-10-20), so the normal run-to-run spread passes but a blank map or a missing object fails.
MIN_CELLS = {                    # seen in run 1 / run 2
    'north wall':    40,       # 190 /  81
    'south wall':   125,       # 250 / 275
    'west wall':     66,       # 133 / 152
    'east wall':     97,       # 195 / 242
    'red box':       12,       #  24 /  26
    'blue pillar':    6,       #  12 /  12
    'green block':   24,       #  48 /  48
}
MIN_OCCUPIED = 347               # 747 / 694
MIN_FREE = 6329                  # 12659 / 12730


def read_yaml(path):
    """The few keys map_saver writes, without needing PyYAML."""
    meta = {}
    for line in open(path):
        key, _, value = line.partition(':')
        meta[key.strip()] = value.strip()
    origin = [float(v) for v in meta['origin'].strip('[]').split(',')]
    return meta['image'], float(meta['resolution']), origin


def read_pgm(path):
    """A binary (P5) PGM: returns width, height and the rows, top row first."""
    data = open(path, 'rb').read()
    fields, pos = [], 0
    while len(fields) < 4:                    # magic, width, height, maxval
        while data[pos:pos + 1].isspace():
            pos += 1
        if data[pos:pos + 1] == b'#':         # comment line
            pos = data.index(b'\n', pos)
            continue
        end = pos
        while not data[end:end + 1].isspace():
            end += 1
        fields.append(data[pos:end])
        pos = end
    width, height = int(fields[1]), int(fields[2])
    pixels = data[pos + 1:]
    return width, height, [pixels[r * width:(r + 1) * width] for r in range(height)]


def main():
    yaml_path = sys.argv[1]
    image, res, origin = read_yaml(yaml_path)
    width, height, rows = read_pgm(os.path.join(os.path.dirname(yaml_path), image))
    print(f'map: {width} x {height} cells of {res:.2f} m = {width * res:.1f} m x {height * res:.1f} m')
    counts = {0: 0, 254: 0, 205: 0}           # occupied, free, unknown in a trinary map
    for row in rows:
        for v in row:
            counts[v] = counts.get(v, 0) + 1
    total = width * height
    print(f'occupied {counts[0]} ({100 * counts[0] / total:.0f} %), free {counts[254]} '
          f'({100 * counts[254] / total:.0f} %), unknown {counts[205]} ({100 * counts[205] / total:.0f} %)')
    failed = []
    if counts[0] < MIN_OCCUPIED:
        failed.append(f'only {counts[0]} occupied cells in the map, need {MIN_OCCUPIED}')
    if counts[254] < MIN_FREE:
        failed.append(f'only {counts[254]} free cells in the map, need {MIN_FREE}')

    def cell(x, y):                           # map coordinates -> pixel value (row 0 = top = max y)
        col = int((x - origin[0]) / res)
        row = height - 1 - int((y - origin[1]) / res)
        return rows[row][col] if 0 <= col < width and 0 <= row < height else None

    for name, (cx, cy, hx, hy) in OBJECTS.items():
        # look for occupied cells in the object's footprint plus one cell all round
        found = 0
        steps_x, steps_y = int(2 * (hx + res) / res) + 1, int(2 * (hy + res) / res) + 1
        for i in range(steps_x):
            for j in range(steps_y):
                if cell(cx - hx - res + i * res, cy - hy - res + j * res) == 0:
                    found += 1
        verdict = 'found' if found >= MIN_CELLS[name] else 'TOO FEW' if found else 'MISSING'
        print(f'{name:12s} at ({cx:+.1f}, {cy:+.1f}): {verdict} ({found} occupied cells)')
        if verdict != 'found':
            failed.append(f'{name}: {found} occupied cells, need {MIN_CELLS[name]}')
    for reason in failed:
        print('FAIL: ' + reason)
    return 1 if failed else 0              # exit code 1: the map does not match the world


if __name__ == '__main__':
    sys.exit(main())
```

## Navigate with Nav2

Navigation needs the map and the robot's pose in it. Nav2's classic answer is `map_server` plus AMCL (a particle filter); with SLAM Toolbox you can instead load the saved pose graph in **localization mode**, which matches scans against the stored ones and publishes the same `map → odom` transform as before. That keeps one tool for mapping and localizing.

<CodeSource path="examples/month-4/slam-nav/m4_nav/config/slam_localization.yaml" />

```yaml

slam_toolbox:
  ros__parameters:
    mode: localization
    odom_frame: odom
    map_frame: map
    base_frame: base_footprint
    scan_topic: /scan
    resolution: 0.05
    max_laser_range: 8.0
    minimum_travel_distance: 0.2
    minimum_travel_heading: 0.2
    map_update_interval: 2.0
    map_start_pose: [0.0, 0.0, 0.0]   # where the robot is in the saved map at start (x, y, yaw)
```

`map_start_pose` tells SLAM Toolbox where the robot is in the saved map when it starts. Here the robot spawns at the same place where mapping started, so it is the origin. If you start the robot somewhere else, either set this to the right pose or set it roughly and let scan matching pull it in, which only works for small errors.

### What Nav2 runs

Nav2 is a set of servers coordinated by a behaviour tree. The parameter file [`m4_nav/config/nav2.yaml`](https://github.com/liudicsu/Hardware-learning/blob/main/examples/month-4/slam-nav/m4_nav/config/nav2.yaml) is based on the one shipped with `nav2_bringup`, and the lines changed for m4bot are marked `# m4bot`. Follow one goal through it:

1. **`bt_navigator`** receives the `NavigateToPose` goal and runs a behaviour tree: plan, follow, and on failure try recoveries (clear the costmaps, spin, wait, back up) before giving up.
2. **`planner_server`** plans a path on the **global costmap**, which is the saved map (the static layer) plus obstacles currently seen by the lidar, plus inflation. The planner is NavFn, a grid search.
3. **`controller_server`** follows the path with Regulated Pure Pursuit at up to 0.25 m/s, steering on the **local costmap**, a 3 m × 3 m window around the robot built from the lidar alone. It turns on the spot first when the path points more than 0.785 rad (45°) away from the robot's heading.
4. **`velocity_smoother`** limits acceleration, and **`collision_monitor`** slows or stops the robot if the lidar sees something about to be hit. Its output, `cmd_vel_out_topic: "/diff_drive_controller/cmd_vel"`, is the only line that connects Nav2 to Lesson 5's controller. Because that controller expects `TwistStamped`, every server that publishes velocities has `enable_stamped_cmd_vel: true`.

The robot's shape enters through `footprint`, a rectangle around `base_footprint` from 0.11 m behind to 0.21 m in front and 0.16 m to each side. **Inflation** adds a cost that falls off with distance around every obstacle, out to `inflation_radius: 0.45` m. Cells the footprint would hit are forbidden; inflated cells are allowed but expensive, so the planner keeps a margin where it can and squeezes through narrow gaps only when it must. Goals count as reached within `xy_goal_tolerance` 0.10 m and `yaw_goal_tolerance` 0.15 rad (about 9°).

## When navigation fails

Nav2 failures look alike from the outside: the robot does not move, or it spins and gives up. The cause is almost always one of a few things, and each leaves a trace you can find.

| Symptom | Likely cause | Where to look |
| --- | --- | --- |
| "Lookup would require extrapolation" or "frame does not exist" in the logs | one node runs on wall time while the rest use the simulator's clock (`use_sim_time`) | `ros2 param get <node> use_sim_time` on each node |
| The goal is accepted, nothing moves | velocities go to a topic nobody listens to, or plain `Twist` reaches a controller that wants `TwistStamped` | `ros2 topic info -v /diff_drive_controller/cmd_vel` |
| Planning fails at once | the goal or the robot is inside an obstacle or its forbidden zone; or the map frame is missing because localization did not start | the global costmap in RViz; `ros2 run tf2_tools view_frames` |
| A goal inside an obstacle still returns SUCCEEDED | possibly the planner's `tolerance` (NavFn plans to the nearest free cell within that distance of the goal), possibly the goal checker's `xy_goal_tolerance` (it accepts any stop within that radius); the status alone does not tell you which | compare the final pose with the goal yourself: `tf2_echo map base_footprint` and the distance to the goal you sent |
| The robot stops for no visible reason | the lidar stopped publishing, so the costmaps time out the sensor and the collision monitor sees no data | `ros2 topic hz /scan` |
| The map is smeared or the robot jumps in RViz | odometry badly calibrated, or `map_start_pose` far from the real starting pose | `spin_check.py`; the starting pose |
| The robot will not pass through a doorway that is clearly wide enough | the footprint or `inflation_radius` too large for the gap | the costmaps in RViz |

The new row deserves a word: SUCCEEDED means "stopped within tolerance of where the planner and goal checker decided to go", not "reached the point you asked for". With this lesson's `nav2.yaml`, NavFn's `tolerance: 0.5` lets the planner end its path at a free cell up to 0.5 m from an unreachable goal, and `xy_goal_tolerance: 0.10` then accepts a stop within 0.10 m of that path's end. One of them, or both together, may be what turns a goal inside a pillar into a success. Do not guess which; after every goal, read the final pose (`tf2_echo map base_footprint` with `use_sim_time:=true`), work out its distance to the goal you sent, and treat a distance larger than `xy_goal_tolerance` as a failure your own code must catch.

Start with TF, because every server needs `map → odom → base_footprint` to be complete and current. `ros2 run tf2_tools view_frames` draws the tree (Lesson 3's broken-tree diagnosis works here unchanged); `ros2 run tf2_ros tf2_echo map base_footprint --ros-args -p use_sim_time:=true` shows whether the robot has a pose in the map at all. Note the `use_sim_time:=true`: without it, `tf2_echo` asks for transforms at the computer's time while everything else lives on Gazebo's clock, and it will only ever report extrapolation errors, which is the first row of the table in miniature.

Then look at the costmaps. In RViz, add a Map display on `/global_costmap/costmap` and one on `/local_costmap/costmap`. A goal that sits in the bright forbidden band around an obstacle cannot be reached however good the rest of the setup is, and a doorway whose two inflated edges touch is closed as far as the planner is concerned. Lowering `inflation_radius` opens it; making the footprint smaller than the real robot also opens it, and that is how robots end up scraping door frames. Fix the footprint first, then tune inflation.

<Callout type="tip" title="Read the log from the top">Nav2 prints its recoveries in order ("Running spin", "Running backup", ...) before it finally reports a failure. The first warning before them usually names the real problem, for example a costmap sensor timeout or a failed transform. Scrolling straight to the last line only tells you that it gave up.</Callout>

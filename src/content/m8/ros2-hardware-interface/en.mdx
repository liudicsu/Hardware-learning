## Hardware-component callbacks

control.ros.org (Jazzy) *Writing a Hardware Component*: the class inherits `hardware_interface::{System|Actuator|Sensor}Interface` and implements LifecycleNodeInterface methods plus interface hooks:

- `on_init`
- `on_configure` / `on_cleanup` / `on_shutdown`
- `on_activate` / `on_deactivate`
- `on_error`
- `export_state_interfaces` / `export_command_interfaces` (Jazzy can also auto-export from the `ros2_control` URDF tag)
- optional `prepare_command_mode_switch` / `perform_command_mode_switch`
- **`read`** / **`write`** every control cycle

Open the serial port in `on_configure`; enable in `on_activate`; `read` copies bus state into state interfaces; `write` sends commands. Do not allocate or make blocking Hub calls inside `read`/`write`.

## Managed-node lifecycle ≠ HardwareComponent SM

<Resource id="ros2-node-lifecycle" />

**LOCKED:** the toy below implements the **managed ROS lifecycle node** state machine from [design.ros2.org — Managed nodes](https://design.ros2.org/articles/node_lifecycle.html). It is **not** the `HardwareComponentInterface` state machine. Never equate the two.

| | **Managed ROS lifecycle node** | **ros2_control `HardwareComponentInterface`** |
|---|---|---|
| What it is | Node exposing lifecycle services/topics per the design doc | Plugin implementing `LifecycleNodeInterface`; **not** a freestanding managed node |
| Who transitions | Supervisory process via lifecycle services | `ResourceManager` / Controller Manager (`set_hardware_component_state`, etc.) |
| Error paths | Design: `ErrorProcessing` → Unconfigured or Finalized | Historical issues note behaviour may **not** match the design doc 1:1 — cite [ros2_control#2079](https://github.com/ros-controls/ros2_control/issues/2079) as discussion, not as a second SM to implement |
| Tracing | `rcl_lifecycle_*` on real lifecycle nodes | Hardware path may not emit the same tracepoints — say so |

API pointer: [`HardwareComponentInterface`](https://control.ros.org/rolling/doc/api/classhardware__interface_1_1HardwareComponentInterface.html). Exact Controller Manager transition tables drift by distro — map at prose level; the toy stays on the managed-node design SM only.

Primary states in the design: `Unconfigured`, `Inactive`, `Active`, `Finalized`. From `Unconfigured`, legal outs are `configure` → `Inactive` and `shutdown` → `Finalized`. **`activate` from `Unconfigured` is illegal** and must be **rejected** (state unchanged). That does **not** mean the node can never become Active later — a later legal `configure` then `activate` can succeed. The toy must show recovery, never “one illegal activate ⇒ permanently dead.”

### `lifecycle_sm_toy.py`

Script A: `configure` → `activate` → `Active` (`illegal_rejects=0`).  
Script B: illegal `activate` from `Unconfigured` → rejected; then `configure` → `activate` → `Active` (`illegal_rejects=1`, still `reached_active=1`).  
Script C: `configure` → `activate` → `shutdown` → `Finalized` (`reached_active=1`, `final_state=Finalized`).

```python
#!/usr/bin/env python3
"""lifecycle_sm_toy.py: ROS 2 *managed-node* lifecycle state machine (stdlib).

LOCKED: this toy implements the managed ROS lifecycle node SM from
  https://design.ros2.org/articles/node_lifecycle.html
It is NOT the ros2_control HardwareComponentInterface state machine.
Hardware components are plugins transitioned by ResourceManager /
Controller Manager; do not equate the two SMs (see lesson MDX contrast).

Primary states (design): Unconfigured, Inactive, Active, Finalized.
Supervisory transitions used here: configure, activate, deactivate,
cleanup, shutdown. Illegal requests are rejected and leave the primary
state unchanged — they do NOT permanently brick the node.

Script A: configure → activate → Active.
Script B: activate from Unconfigured (illegal, reject) → still
          Unconfigured; then configure → activate → Active (recovery).
Script C: configure → activate → shutdown → Finalized.
Metrics: illegal_rejects, reached_active, final_state.

Tracing / LTTng / real HardwareComponent load = 本页未运行.
usage: python3 lifecycle_sm_toy.py
"""
from __future__ import annotations

# Primary states from the design doc.
UNCONFIGURED = "Unconfigured"
INACTIVE = "Inactive"
ACTIVE = "Active"
FINALIZED = "Finalized"

# Legal edges: (state, transition) -> new_state
# From design: Unconfigured --configure--> Inactive
#              Unconfigured --shutdown--> Finalized
#              Inactive --activate--> Active
#              Inactive --cleanup--> Unconfigured
#              Inactive --shutdown--> Finalized
#              Active --deactivate--> Inactive
#              Active --shutdown--> Finalized
LEGAL = {
    (UNCONFIGURED, "configure"): INACTIVE,
    (UNCONFIGURED, "shutdown"): FINALIZED,
    (INACTIVE, "activate"): ACTIVE,
    (INACTIVE, "cleanup"): UNCONFIGURED,
    (INACTIVE, "shutdown"): FINALIZED,
    (ACTIVE, "deactivate"): INACTIVE,
    (ACTIVE, "shutdown"): FINALIZED,
}


class ManagedLifecycleNode:
    """Minimal managed-node lifecycle — design adjacency only."""

    def __init__(self) -> None:
        self.state = UNCONFIGURED
        self.illegal_rejects = 0
        self.transition_log: list[str] = []

    def request(self, transition: str) -> bool:
        key = (self.state, transition)
        if key not in LEGAL:
            self.illegal_rejects += 1
            self.transition_log.append(
                f"{transition}:REJECT(from={self.state})"
            )
            return False
        new_state = LEGAL[key]
        self.transition_log.append(
            f"{transition}:OK({self.state}->{new_state})"
        )
        self.state = new_state
        return True


def run_script(name: str, steps: list[str]) -> dict:
    node = ManagedLifecycleNode()
    for step in steps:
        node.request(step)
    # reached_active: successfully entered Active at least once
    reached = 1 if any("->Active" in e for e in node.transition_log) else 0
    result = {
        "script": name,
        "steps": steps,
        "illegal_rejects": node.illegal_rejects,
        "reached_active": reached,
        "final_state": node.state,
        "log": node.transition_log,
    }
    return result


def main() -> None:
    print(
        "lifecycle_sm_toy sm=ros2_managed_node "
        "source=design.ros2.org/articles/node_lifecycle.html"
    )
    print(
        "note: NOT HardwareComponentInterface SM; "
        "ResourceManager transitions that plugin (prose map only)"
    )

    a = run_script("A", ["configure", "activate"])
    b = run_script("B", ["activate", "configure", "activate"])
    c = run_script("C", ["configure", "activate", "shutdown"])

    for r in (a, b, c):
        print(
            f"script_{r['script']}: steps={','.join(r['steps'])} "
            f"illegal_rejects={r['illegal_rejects']} "
            f"reached_active={r['reached_active']} "
            f"final_state={r['final_state']}"
        )
        print(f"script_{r['script']}_log={' | '.join(r['log'])}")

    assert a["illegal_rejects"] == 0
    assert a["reached_active"] == 1
    assert a["final_state"] == ACTIVE

    assert b["illegal_rejects"] == 1
    assert b["reached_active"] == 1
    assert b["final_state"] == ACTIVE
    # LOCKED: illegal activate must NOT mean permanently dead.
    assert b["final_state"] == ACTIVE
    print("never_permanent_death_after_illegal_activate=1")

    assert c["illegal_rejects"] == 0
    assert c["reached_active"] == 1
    assert c["final_state"] == FINALIZED
    print("reached_finalized_via_shutdown=1")
    print(
        "ok: managed-node lifecycle toy "
        "(LTTng/ros2_tracing/HW plugin load 本页未运行)"
    )


if __name__ == "__main__":
    main()
```

## JointLimiter

Jazzy joint_limiting docs log lines like `Using JointLimiter for joint 'joint1' ... has position limits: true [-1, 1]` and print velocity limits. Declare limits in the `ros2_control` XML so bad commands do not request infinite velocity before lesson 8.5's software soft limits.

## Real-time loop discipline

The ROS 2 Real-Time-Programming demo (`ros2/ros2_documentation` jazzy branch `Real-Time-Programming.rst`) in one line: the real-time loop must finish on time with only small jitter — avoid page faults, dynamic allocation and unbounded blocking on the hot path. ROS 1 was not designed this way; do not stuff blocking USB retries into `write()`.

```python
#!/usr/bin/env python3
"""servo_bus_sim.py: simulate hardware read/write cycle jitter → timeout counts.

Models a ros2_control-style loop at CONTROL_HZ. Each tick must finish both
read() and write() within the period. Bus latency is base + jitter; when the
sum exceeds the period the tick is a TIMEOUT (deadline miss).

Modes:
  naive — always pay full read+write cost.
  budget_guard — if projected read+write would exceed the period, skip the
                 blocking write and apply a cheap hold (HOLD_MS). That can still
                 miss if read alone is huge, but usually cuts timeouts.

Pinned seed and constants keep expected/ stable. Pure CPU; no real serial.
The so101_hw/ skeleton beside this file is for your Jazzy workspace
(marked 「本页未运行」 in the lesson).
usage: python3 servo_bus_sim.py
"""
from __future__ import annotations

import random

CONTROL_HZ = 100
PERIOD_MS = 1000.0 / CONTROL_HZ  # 10.0
BASE_READ_MS = 2.0
BASE_WRITE_MS = 2.5
JITTER_MS = 6.0  # uniform [0, JITTER_MS] added to read and to write
HOLD_MS = 0.4  # cheap "hold last command" path under budget_guard
TICKS = 200
SEED = 8


def run(budget_guard: bool) -> tuple[int, float, int]:
    """Return (timeouts, max_overshoot_ms, holds_used)."""
    rng = random.Random(SEED)
    timeouts = 0
    max_over = 0.0
    holds = 0
    for _ in range(TICKS):
        read_ms = BASE_READ_MS + rng.random() * JITTER_MS
        write_ms = BASE_WRITE_MS + rng.random() * JITTER_MS
        if budget_guard and (read_ms + write_ms) > PERIOD_MS:
            total = read_ms + HOLD_MS
            holds += 1
        else:
            total = read_ms + write_ms
        over = total - PERIOD_MS
        if over > 0:
            timeouts += 1
            max_over = max(max_over, over)
    return timeouts, max_over, holds


def main() -> None:
    t_naive, o_naive, _ = run(False)
    t_guard, o_guard, holds = run(True)
    print(f"servo_bus_sim control_hz={CONTROL_HZ} period_ms={PERIOD_MS:g} ticks={TICKS} seed={SEED}")
    print(f"naive_timeouts={t_naive} naive_max_overshoot_ms={o_naive:.3f}")
    print(f"guard_timeouts={t_guard} guard_max_overshoot_ms={o_guard:.3f} holds={holds}")
    print(f"timeout_reduction={t_naive - t_guard}")
    print("ok: CPU bus jitter toy (no real STS3215 bus, page not run)")


if __name__ == "__main__":
    main()
```

## Common mistakes

- **Equating managed-node lifecycle services with HardwareComponent transitions.** Different actors; toy is managed-node only.
- **Teaching “illegal activate ⇒ permanently dead.”** Reject, stay Unconfigured, then recover via configure → activate.
- **Opening the serial port in `read`.** Configure once in `on_configure` so the period stays deterministic.
- **`new`-ing vectors on every `write`.** Preallocate at configure time.
- **Skipping JointLimiter.** Lesson 8.5's software watchdog does not replace declaring position/velocity limits to ros2_control.
- **Expecting this site's CI to load your `.so`.** Student package CI ≠ Hardware-learning website CI.
